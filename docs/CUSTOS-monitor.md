# CUSTOS Monitor — сервер мониторинга. Техническое задание

Версия ТЗ: 1.0 от 12.10.2026. Второй документ проекта — `CUSTOS-client.md` (программа для Windows). Общий контракт между ними вынесен в приложение A, оно одинаково в обоих файлах.

## 0. Как работать с этим документом

- **Заказчик** — системный администратор, не программист. Он сам разворачивает сервер (у себя через CloudPanel: nginx + PHP-FPM + MariaDB), присылает ошибки из журналов и скриншоты.
- **Как отдавать код.** Файлы целиком, SQL-миграции отдельными файлами, точные команды установки и обновления. После каждого шага — короткий список, что проверить.
- **Язык.** Общение на русском. Код, комментарии, имена, сообщения коммитов — на английском: проект будет опубликован на GitHub под лицензией **GPL-3.0**. Интерфейс сайта на русском и английском.
- **Порядок.** Работаем по этапам из раздела 13. Сервер разрабатывается независимо от клиента: для проверки есть имитатор агентов (раздел 12).
- **Если решение в ТЗ не работает**, предложить замену и объяснить последствия. Если приходится менять приложение A, это нужно явно сказать: правку переносят в оба файла.

## 1. Что делаем

**CUSTOS Monitor** — веб-приложение для централизованного наблюдения за резервным копированием на компьютерах с агентом CUSTOS и управления им.

- Главная задача — **замечать не только упавшие бэкапы, но и те, что вообще не случились**: задание отключили, служба зависла, машина выключена.
- Показывает статусы, историю, журналы, прогресс в реальном времени, место в хранилищах.
- Позволяет запускать задания, редактировать их, раздавать шаблоны и обновления агентов.
- Шлёт уведомления в Telegram и на почту, отдаёт данные в Zabbix.
- Одна организация, локальная сеть. Агенты прекрасно работают и без сервера.
- Масштаб: у автора около 20 машин, проект рассчитан на сотни агентов.

## 3. Структура и установка

### 3.1. Структура

```
server/
  public/            index.php (фронт-контроллер), assets/ (css, js, vendor/chart.js)
  src/               Http/ (роутер, контроллеры), Domain/ (сервисы), Infra/ (БД, крипто, почта, Telegram)
  templates/         страницы
  lang/              ru.php, en.php
  migrations/        001_init.sql, 002_…sql
  bin/               install.php, migrate.php, cron.php
  tools/             fake-agent.php (раздел 12)
  zabbix/            custos_template.yaml
  config/            config.example.php → config.php; keys/ (ключи сервера, права 600)
  composer.json
```

### 3.2. Установка (оформить в `server/INSTALL.md`, по-русски и по-английски)

1. **CloudPanel:** создать PHP-сайт (PHP 8.4), домен вроде `custos.lan` (локальный DNS), корень — `.../server/public`. Создать базу MariaDB и пользователя.
2. Загрузить папку `server/`, выполнить `composer install --no-dev`.
3. Скопировать `config/config.example.php` в `config/config.php`, указать доступ к базе и адрес сайта.
4. Выполнить `php bin/install.php`. Скрипт проверяет расширения PHP, применяет миграции, создаёт ключи сервера, спрашивает логин и пароль первого администратора, генерирует ключ регистрации агентов, токены Zabbix и настенного режима.
5. Добавить cron: `* * * * * php /путь/server/bin/cron.php`.
6. Для nginx без CloudPanel дать пример конфигурации: `try_files $uri /index.php?$query_string;` и **`client_max_body_size 10m`**, потому что журналы от агентов до 8 МБ.
7. Обновление сервера: заменить файлы, выполнить `php bin/migrate.php`.

## 4. Доступ и безопасность

- **Вход по локальным учётным записям.** Ролей нет: все пользователи сайта — администраторы. Есть страница пользователей: создать, отключить, сбросить пароль.
- **Пароли** хранятся через `password_hash` (Argon2id, если доступен, иначе bcrypt).
- **Сессии:** `httponly`, `SameSite=Lax`, `secure` при HTTPS, новый id сессии при входе, тайм-аут бездействия (по умолчанию 8 часов).
- CSRF-токен на всех формах. Не больше 5 неудачных входов за 15 минут на пару «IP + логин».
- **Ограничение по IP-подсетям** (списки CIDR, пустой список = без ограничений):
  - отдельно для сайта;
  - отдельно для API агентов;
  - отдельно для Zabbix и настенного режима.
- Только подготовленные запросы к базе, весь вывод экранируется.
- **Журнал действий** пользователей:
  - входы, в том числе неудачные;
  - управление пользователями;
  - подтверждение, отключение и удаление агентов;
  - правки заданий, команды, применение шаблонов, загрузка обновлений, изменение настроек.
  - Записи хранятся столько же, сколько история (раздел 11). Просмотр с фильтром по дате и пользователю.
- **Ключи сервера** (A.2) лежат в `config/keys/`, вне веб-корня, с правами 600.
- **Секреты.** Пароли из редактора заданий шифруются на ключ агента сразу при отправке формы (A.2). Хранятся только внутри ещё не доставленной команды и стираются из неё после доставки или истечения срока. В открытом виде сервер их не хранит никогда.
- Двухфакторная аутентификация — позже.

## 6. Логика статусов — сердце системы

### 6.1. На связи и не на связи

- Агент **на связи**, если последний heartbeat был не раньше `offline_after_min` минут назад (по умолчанию 60). Иначе он **не на связи**: серая надпись, но не проблема и не уведомление.
- Каждый heartbeat продлевает текущий интервал в `agent_presence`. Если с прошлого heartbeat прошло больше трёх интервалов, начинается новый интервал.

### 6.2. Ожидаемые слоты

- Из `schedule` задания (A.9) в **часовом поясе агента** вычисляются слоты: моменты, когда задание должно было стартовать. Расчёт делается через `DateTimeImmutable` с поясом IANA, переходы на летнее время учитываются.
- У заданий `manual`, отключённых заданий и неподтверждённых или отключённых агентов ожиданий нет.
- Новое задание проверяется только с момента появления на сервере. Изменённое — по новому расписанию с момента изменения.

### 6.3. Проверка пропусков (cron, раз в минуту)

Для каждого слота `T`, у которого наступило время `T + missed_grace_min` (по умолчанию 15 минут, одна настройка на всю систему):

1. Если есть запуск с `scheduled_for = T` или запуск, начавшийся в интервале `[T − 1 мин; T + grace]`, слот **выполнен**.
2. Если задание сейчас в очереди агента или выполняется (по данным heartbeat), решение откладывается до следующей минуты: очередь последовательная, и задание может стартовать позже.
3. Если машина была на связи хоть раз в интервале `[T; T + grace]` — **`missed`**. Это проблема: машина работала, а бэкап не сделан.
4. Иначе — **`missed_offline`**, «пропущено, машина выключена». Мягкая пометка, не проблема.

Закрытие пропуска:
- `missed` закрывается любым успешным запуском после `T`.
- `missed_offline` закрывается догоняющим запуском с `scheduled_for = T` или любым успешным запуском после `T`.

Для заданий **по таймеру** (`interval`): если агент был на связи без перерыва дольше `interval + grace`, а запусков за это время не было, задание получает `missed`.

Так выходные и ночи не создают лавины предупреждений: выключенная рабочая станция получает только серую пометку, а утром догоняющий запуск её снимает.

### 6.4. Давно нет успешной копии

Если последняя успешная копия задания по расписанию старше `stale_days` дней (по умолчанию 7), ставится мягкая пометка `stale`. Это не тревога: сотрудник может быть в отпуске. Уведомление не отправляется.

### 6.5. Аномалии

`source_bytes` и `source_files` запуска сравниваются с медианой последних 10 успешных запусков того же задания. Падение больше чем на 30 % или рост больше чем вдвое дают пометку «аномалия» на запуске и на задании. Это признак сломанного источника или работы шифровальщика. Пороги настраиваются.

### 6.6. Итоговый статус задания

Для показа берётся самый важный из действующих: `running` → `error` → `missed` → `warning` → аномалия → `missed_offline` → `stale` → `ok` → «ещё не выполнялось» → `disabled`.

Цвета: красный только для `error` и `missed`; жёлтый для `warning` и аномалии; серый для `missed_offline`, `stale`, `offline`; зелёный для `ok`; синий для `running`. Прерванный пользователем запуск (`aborted`) проблемой не считается.

## 7. Интерфейс сайта

Тема оформления: авто по умолчанию, светлая, тёмная; выбирается в профиле пользователя. Язык тоже выбирается в профиле. Отдельная мобильная версия — позже, но вёрстка не должна разваливаться на узком экране.

### 7.1. Дашборд (главная)

- **Сводка:**
  - машины: всего, на связи, ждут подтверждения;
  - задания: в норме, с предупреждениями, ошибки, пропущено, выполняется сейчас;
  - хранилища: наименьший остаток места и прогноз «закончится примерно через N дней»;
  - объём, записанный за последние сутки.
- **«Требует внимания»:** открытые проблемы (`error`, `missed`) наверху. Ниже отдельным спокойным блоком мягкие пометки: выключенные машины с пропусками, давно нет успешной копии, аномалии.
- **«Сейчас выполняется»:** полосы прогресса с текущим файлом. Обновляются в реальном времени.
- **Тепловая карта за 30 дней:** ячейка на день, цвет по худшему результату дня. Клик открывает запуски этого дня.
- **Уведомления** (раздел 7.7) и агенты с устаревшей версией.
- Данные обновляются каждые 15 секунд через JSON-эндпоинт, без перезагрузки страницы.

### 7.2. Машины × задания

Строки сгруппированы по группам машин. В каждой строке:
- имя машины, «на связи» или «нет», последний контакт, версия агента;
- задания этой машины цветными «плашками» статуса. Подсказка показывает последний и следующий запуск, клик открывает задание.
- Фильтр по группе. Полноценные поиск и фильтры — позже.

### 7.3. Страница машины

- **Карточка:** имя (можно переименовать), группа, IP, ОС, версия агента, часовой пояс, первое появление, последний контакт, отпечаток ключа.
- **Действия:** подтвердить, отключить, удалить (с подтверждением; история удаляется вместе с машиной), обновить агента.
- **Настройки агента**, которые передаются командой `settings.update`: пароль программы (задать или сбросить), режим трея, «разрешить всем менять задания», срок хранения журналов, детальность журнала, приоритет.
- **Задания:** описание человеческим языком (раздел 7.6), статус, следующий ожидаемый запуск. Кнопки: запустить, остановить, включить или отключить, изменить, клонировать, удалить, история.
- **Текущий запуск в реальном времени:** этап, процент, текущий файл, скорость, оставшееся время.
- **Хранилища:** назначения, свободное место с прогнозом, наборы копий, которые реально лежат в хранилище (A.8), с датой последней проверки. Наборы, не прошедшие проверку, выделены красным.
- **Учётные данные:** только имена пользователей и отметка «пароль задан».

### 7.4. Страница задания и запуска

- **Задание:**
  - описание и полные настройки;
  - история запусков с фильтром;
  - графики во времени: размер источника, записанный объём, длительность, с отметками аномалий;
  - ожидаемые слоты и пропуски;
  - **история версий**: кто и когда менял (с сайта или на месте), просмотр различий, кнопка «вернуть эту версию».
- **Запуск:** все поля A.5, результат по назначениям, хвост журнала, полный журнал.
  - Если полного журнала на сервере нет (у успешного запуска), есть кнопка «Запросить журнал у агента» (`log.fetch`).

### 7.5. Редактор задания

- Все поля A.9 с теми же правилами проверки, что в клиенте. Например, 7z недоступен, если среди назначений есть FTP, WebDAV или S3; у этого варианта есть подсказка с объяснением.
- **Подсказки** с описанием типов копий (полная, инкрементальная, дифференциальная, зеркало). Тексты те же, что в клиенте.
- **Секреты** вводятся в отдельные поля и сразу шифруются на ключ агента. Уже заданные пароли не показываются, рядом только отметка «задан» и кнопка «заменить».
- После сохранения уходит команда `task.upsert`, на странице видно «ожидает доставки» до подтверждения агентом. Если агент вернул `conflict`, создаётся уведомление, а перезаписанная версия попадает в историю.
- Если у агента выключено «Разрешить серверу менять задания», редактор открывается только для чтения с объяснением.

### 7.6. Описание задания человеческим языком

Функция строит из JSON строку на русском или английском. Пример:

> Инкрементальная копия D:\Data → \\\\fileserver\docs · ежедневно в 00:00 · без сжатия · хранить 12 полных копий · VSS

В ней должно быть видно расписание, тип, источники, назначения, сжатие, хранение и события. Цель — чтобы ошибка в настройке бросалась в глаза сразу. Например, у автора задание «EveryMonth 01:00» на самом деле ежедневное.

### 7.7. Ненавязчивые уведомления (колокольчик)

- Задание изменено на месте (`updated_by = local:…`): кто, что, когда, со ссылкой на различия.
- Новый агент ждёт подтверждения, повторная регистрация.
- Конфликт: правка перезаписала чужую версию.
- Агент с устаревшей версией.
- Команда отклонена или завершилась ошибкой.

Уведомления можно отмечать прочитанными, они не дублируются в Telegram и почту.

### 7.8. Настройки

- **Общие:** название сервера, язык по умолчанию.
- **Пороги:**
  - `offline_after_min` = 60;
  - `missed_grace_min` = 15;
  - `stale_days` = 7;
  - пороги аномалий: 30 % и ×2;
  - `heartbeat_interval_s` = 60.
- **Сроки хранения:**
  - история запусков, присутствие и журнал действий — **12 месяцев**;
  - полные журналы — 90 дней.
- **Агенты:** ключ регистрации (показать, сгенерировать новый), отпечаток ключа сервера.
- Списки IP-подсетей (раздел 4).
- Уведомления (раздел 9), токен Zabbix, токен настенного режима.
- Пользователи и журнал действий.

### 7.9. Настенный режим

Адрес `/wall?token=…`, без входа. Остаётся только ограничение по IP.
- Крупные плитки, проблемы сверху, тёмное оформление.
- Автообновление каждые 30 секунд.

## 8. Управление агентами и заданиями

- **Подтверждение агента:** список ожидающих с именем, IP, ОС и отпечатком ключа, который можно сверить с окном программы на машине. При повторной регистрации есть выбор: заменить существующего агента (история и задания сохраняются) или завести нового.
- **Команды** (A.4): запустить, остановить, пауза, включить, отключить, изменить, удалить, обновить настройки, запросить журнал, инвентаризация, обновление. Сроки действия по умолчанию:
  - запуск, остановка и пауза — 1 час;
  - изменения — 7 дней;
  - обновление — 3 дня.

  Статус каждой команды виден на странице машины.
- **Шаблоны заданий:**
  - шаблон создаётся с нуля или из существующего задания;
  - применяется к группе или к выбранным машинам: на каждой создаётся своё задание через `task.upsert`, а связь с шаблоном сохраняется;
  - повторное применение обновляет связанные задания;
  - **секреты в шаблоне не хранятся**, они вводятся при каждом применении.
- **Обновления агентов:**
  - загрузить пакет (zip с `manifest.json`, A.10). Сервер проверяет версию, считает SHA-256 и подписывает `"{version}\n{sha256}"`;
  - отметить версию как текущую;
  - кнопки «обновить машину», «обновить группу», «обновить все устаревшие»;
  - распределение версий по машинам видно на дашборде.

## 9. Уведомления в Telegram и на почту

- **Отправляются только проблемы: `error` и `missed`.** Одно сообщение на проблему в момент её открытия. Повторов, сообщений о восстановлении и сводок нет.
- Проблемы, открытые за один проход cron, собираются в **одно сообщение**, сгруппированное по машинам. Так не будет потока сообщений, если что-то сломалось сразу на многих машинах.
- Текст сообщения: машина, задание, что случилось (ошибка с первой строкой `error_message` или «не запустилось по расписанию в 00:00, машина была включена»), ссылка на страницу задания.
- **Telegram:** токен бота, один или несколько chat_id. Можно указать прокси (HTTP или SOCKS5), если `api.telegram.org` недоступен с сервера.
- **Почта:** SMTP (хост, порт, шифрование, логин, пароль), адрес отправителя, список получателей. Отправка через PHPMailer.
- Для каждого канала есть кнопка «Отправить тестовое сообщение».
- Получатели одни на всю систему.

## 10. Zabbix

**Эндпоинты** (GET, токен в `?token=` или заголовке `X-Custos-Token`, плюс ограничение по IP):

- `/api/zabbix/discovery/agents` → `[{"{#AGENT_ID}": "...", "{#AGENT}": "PC-01", "{#GROUP}": "Рабочие станции"}]`
- `/api/zabbix/discovery/tasks` → `[{"{#AGENT_ID}": "...", "{#AGENT}": "...", "{#TASK_ID}": "...", "{#TASK}": "Documents"}]`
- `/api/zabbix/status` → одним ответом все статусы:
  - `agents.<id>`: `online`, `last_seen_s`, `version`;
  - `tasks.<id>`: `status`, `status_code`, `last_success_age_s`, `last_run_status`, `last_bytes_written`, `anomaly`;
  - `summary`.

  `status_code` — число для триггеров: 0 ok, 1 running, 2 warning, 3 missed_offline, 4 stale, 5 missed, 6 error, 9 disabled или ещё не выполнялось.
- `/api/health` (без токена) → `{"status": "ok", "db": "ok", "cron_lag_s": 12}`. Ответ **503**, если база недоступна или cron не запускался дольше 5 минут. Остановившийся cron незаметно отключил бы проверку пропусков, поэтому это важно.

**Шаблон** `zabbix/custos_template.yaml` (у автора Zabbix 8.0; формат экспорта проверить под эту версию):

- Макросы: `{$CUSTOS.URL}`, `{$CUSTOS.TOKEN}`, `{$CUSTOS.OFFLINE.MAX}` = 24h.
- Главный HTTP-элемент `status` (каждую минуту) и зависимые элементы с JSONPath. Так весь мониторинг стоит один запрос в минуту.
- Правила обнаружения агентов и заданий (раз в час).
- **Триггеры:**
  - ошибка задания — High;
  - пропуск — Average;
  - давно нет успешной копии — Warning;
  - агент не на связи дольше `{$CUSTOS.OFFLINE.MAX}` — Warning (полезно для серверов);
  - `/api/health` не `ok` — High;
  - нет данных от главного элемента 10 минут, то есть сайт недоступен — High.

## 11. Обслуживание

**`bin/cron.php`** запускается раз в минуту и защищён от параллельного запуска блокировкой. Что он делает:

- закрывает интервалы присутствия;
- проверяет слоты, пропуски, `stale`;
- открывает и закрывает проблемы, отправляет уведомления;
- снимает истёкшие команды и стирает в них секреты;
- раз в час пересчитывает прогнозы места;
- раз в сутки чистит старые данные по срокам из 7.8 и `nonces` старше 10 минут.

Время последнего прохода записывается, его использует `/api/health`.

**Прогноз места:** линейный тренд свободного места за 30 дней по каждому назначению → «≈ N дней до заполнения». Если место не убывает, пишется «не убывает».

**Экспорт в CSV:** история запусков за период с фильтрами. UTF-8 с BOM и разделителем `;`, чтобы русский Excel открывал файл без настройки.

## Приложение A. Общий контракт клиента и сервера

> Этот раздел **одинаков** в `CUSTOS-client.md` и `CUSTOS-monitor.md`. Клиент и сервер разрабатываются в разных чатах, поэтому этот текст единственное, что их связывает. Если в одном чате контракт пришлось изменить, правку нужно перенести в оба файла и увеличить версию протокола.

Версия протокола: **1**.

### A.1. Общие правила

- Транспорт: HTTP или HTTPS, JSON в UTF-8, `Content-Type: application/json`.
- Базовый адрес: `{server_url}/api/v1/`. `server_url` задаётся в клиенте, например `http://custos.lan`. Сервер может стоять и в подпапке.
- Каждый запрос агента несёт заголовок `X-Custos-Protocol: 1`.
- Время везде в UTC, формат ISO 8601: `2026-10-12T21:00:00Z`. Агент дополнительно сообщает свой часовой пояс в формате IANA (`Europe/Moscow`). В .NET его даёт `TimeZoneInfo.TryConvertWindowsIdToIanaId`.
- Идентификаторы: UUID v4 в виде строк. Агент сам генерирует id заданий, назначений, источников, учётных данных и запусков. Сервер генерирует `agent_id` и id команд.
- Сжатые поля (журналы): gzip, затем base64, поле с суффиксом `_gz_b64`.
- Размер тела запроса не больше 8 МБ. Полный журнал обрезается до 5 МБ после сжатия.

### A.2. Ключи и подписи

HTTP внутри локальной сети допустим, потому что подлинность обеих сторон обеспечивают подписи, а не транспорт.

- **Ключ агента.** RSA-3072, создаётся при первом запуске службы. Закрытый ключ хранится в `C:\ProgramData\CUSTOS\` под защитой DPAPI от имени SYSTEM.
- **Ключ сервера.** RSA-3072, создаётся при установке сервера (`bin/install.php`). Закрытый ключ лежит вне веб-корня.
- **Подпись:** RSASSA-PKCS1-v1_5 + SHA-256, результат в base64. PHP: `openssl_sign(..., OPENSSL_ALGO_SHA256)`. .NET: `RSA.SignData(..., HashAlgorithmName.SHA256, RSASignaturePadding.Pkcs1)`.
- **Отпечаток ключа:** первые 16 hex-символов SHA-256 от DER открытого ключа, группами по 4: `3F2A-91C0-77DE-0B14`. Показывается в GUI агента и на сайте, чтобы администратор мог их сверить.

**Запрос агента** (всё, кроме регистрации) несёт заголовки:

```
X-Custos-Agent: <agent_id>
X-Custos-Time: <unix-время, секунды>
X-Custos-Nonce: <32 hex-символа, случайные>
X-Custos-Signature: <base64>
```

Подписывается строка `"{METHOD}\n{PATH}\n{TIME}\n{NONCE}\n{sha256hex(body)}"`, где `PATH` — путь запроса вместе со строкой запроса, как он пришёл на сервер (`/api/v1/agent/heartbeat`). Для пустого тела берётся SHA-256 от пустой строки.

Сервер проверяет подпись открытым ключом агента, расхождение времени (не больше 300 с) и уникальность nonce для этого агента в течение 10 минут. При ошибке отвечает 401.

**Ответ сервера** несёт заголовки `X-Custos-Time` и `X-Custos-Signature`. Подписывается строка `"{TIME}\n{NONCE из запроса}\n{sha256hex(body)}"`. Агент проверяет её закреплённым открытым ключом сервера. Ответ с неверной подписью агент отбрасывает так же, как недоступность сервера, и пишет об этом в журнал. Поэтому подменить команды в сети нельзя.

**Секреты, которые сервер передаёт агенту** (пароли шар, FTP, ключи S3 и SFTP, пароль архива), шифруются гибридно. Случайный ключ AES-256 шифруется RSA-OAEP (SHA-1, MGF1-SHA1) на открытом ключе агента, сами данные шифруются AES-256-GCM.

`secret_enc` = base64( зашифрованный ключ, 384 байта ‖ nonce, 12 байт ‖ шифртекст ‖ tag, 16 байт ).

- PHP: `openssl_public_encrypt(..., OPENSSL_PKCS1_OAEP_PADDING)` и `openssl_encrypt('aes-256-gcm', ..., OPENSSL_RAW_DATA, $nonce, $tag)`.
- .NET: `RSA.Decrypt(..., RSAEncryptionPadding.OaepSHA1)` и `AesGcm`.

Агент расшифровывает секрет и сразу сохраняет его через DPAPI. **Сервер не хранит секреты в открытом виде и никогда не получает их от агента.**

**Пароль программы** передаётся только как хэш: `pbkdf2-sha256$<итерации>$<salt base64>$<hash base64>`, 200 000 итераций, соль 16 байт, хэш 32 байта. Сервер вычисляет его через `hash_pbkdf2`, агент через `Rfc2898DeriveBytes.Pbkdf2`.

### A.3. Регистрация агента

1. Администратор задаёт на сервере общий ключ регистрации.
2. Агент отправляет `POST /api/v1/agent/register` без заголовков подписи:

```json
{
  "registration_key": "общий-ключ",
  "hostname": "PC-01",
  "machine_guid": "значение HKLM\\SOFTWARE\\Microsoft\\Cryptography\\MachineGuid",
  "os": "Windows 11 Pro 24H2 (26100)",
  "agent_version": "1.0.0",
  "time_zone": "Europe/Moscow",
  "public_key": "-----BEGIN PUBLIC KEY-----\n...",
  "proof": "base64 подписи строки \"{registration_key}\\n{hostname}\\n{machine_guid}\" ключом агента"
}
```

3. Ответ `200`:

```json
{ "agent_id": "uuid", "status": "pending", "server_public_key": "-----BEGIN PUBLIC KEY-----\n...", "server_name": "CUSTOS" }
```

   Неверный ключ: `403 bad_registration_key`. Агент закрепляет ключ сервера (TOFU) и показывает в GUI «Ожидает подтверждения на сервере» с отпечатками обоих ключей.
4. Администратор подтверждает агента на сайте. До подтверждения сервер принимает от агента только heartbeat. Отчёты о запусках копятся в очереди агента.
5. **Повторная установка.** Если с тем же `machine_guid` уже есть агент, новая регистрация попадает в ожидающие с пометкой «повторная регистрация». Администратор выбирает: заменить существующий (история и задания сохраняются, ключ меняется) или завести новый.
6. Если сервер отвечает `404 unknown_agent` (агента удалили), агент сбрасывает `agent_id` и регистрируется заново.

### A.4. Heartbeat и команды

`POST /api/v1/agent/heartbeat` отправляется каждые `heartbeat_interval_s` секунд (по умолчанию 60). Это быстрый «пульс», через него же приходят команды.

Запрос:

```json
{
  "agent_version": "1.0.0",
  "config_revision": 42,
  "time_zone": "Europe/Moscow",
  "service_started_at": "2026-10-12T05:01:10Z",
  "state": "idle",
  "running": null,
  "queue": ["task-uuid-2", "task-uuid-5"]
}
```

`state`: `idle` или `running`. Во время работы `running` = `{"run_id": "...", "task_id": "..."}`. `queue` — задания, стоящие в очереди.

Ответ:

```json
{
  "status": "approved",
  "server_time": "2026-10-12T13:00:00Z",
  "heartbeat_interval_s": 60,
  "want_config": false,
  "commands": [
    { "id": "cmd-uuid", "kind": "task.run", "payload": { "task_id": "..." }, "expires_at": "2026-10-12T14:00:00Z" }
  ]
}
```

- `status`: `pending`, `approved` или `disabled`. Отключённый (`disabled`) агент продолжает работать автономно и шлёт только heartbeat раз в 10 минут.
- `want_config: true` значит, что сервер просит полный снимок конфигурации (A.6). Так бывает после подтверждения или при расхождении `config_revision`.
- Команду с истёкшим `expires_at` агент отклоняет.

Результат команды: `POST /api/v1/agent/commands/{id}/result` с телом `{"status": "done|failed|rejected", "message": "..."}`.

| `kind` | `payload` | Что делает агент |
|---|---|---|
| `task.run` | `{task_id}` | Ставит задание в очередь с `trigger: "remote"` |
| `task.stop` | `{task_id}` | Прерывает выполнение (статус `aborted`) |
| `task.pause` / `task.resume` | `{task_id}` | Пауза и продолжение |
| `task.enable` / `task.disable` | `{task_id}` | Включает или отключает задание |
| `task.upsert` | `{task, base_revision, secrets}` | Создаёт или изменяет задание (см. ниже) |
| `task.delete` | `{task_id}` | Удаляет задание (сами копии в хранилище не трогает) |
| `settings.update` | `{settings}` (частично) | Меняет настройки из A.9, кроме локальных |
| `log.fetch` | `{run_id}` | Выгружает полный журнал запуска (A.7) |
| `inventory.refresh` | `{}` | Отправляет инвентаризацию (A.8) |
| `update.install` | `{version, sha256, signature}` | Скачивает и ставит обновление (A.10) |

Если на агенте выключено «Разрешить серверу менять задания», команды `task.upsert`, `task.delete`, `task.enable`, `task.disable` и `settings.update` отклоняются (`rejected`).

**`task.upsert` и конфликты.** `secrets` — объект `{ "<credential_id>": { "kind", "user", "domain", "secret_enc" } }`, где `secret_enc` зашифрован по A.2. Правило конфликтов: **побеждает последняя правка**. Агент применяет изменение, даже если `base_revision` не совпадает с текущей ревизией задания. В этом случае он отвечает `done` с `message: "conflict: local revision N overwritten"` и прикладывает перезаписанную версию к ближайшему снимку конфигурации в поле `overwritten`. Новая ревизия задания = max(локальная, `base_revision`) + 1, `updated_by` = `server:<логин>`.

### A.5. Запуски

`POST /api/v1/agent/runs/start`:

```json
{
  "run_id": "uuid", "task_id": "uuid", "task_revision": 7,
  "backup_type": "incremental",
  "trigger": "schedule",
  "scheduled_for": "2026-10-12T21:00:00Z",
  "started_at": "2026-10-12T21:00:02Z"
}
```

- `trigger`: `schedule`, `catch_up` (догоняющий запуск после выключения), `manual` (кнопка в GUI) или `remote` (команда с сервера).
- `scheduled_for` — слот расписания, к которому относится запуск. Для `schedule` и `catch_up` он обязателен, для `manual` и `remote` равен `null`. По нему сервер сопоставляет запуски с ожидаемым расписанием.

`POST /api/v1/agent/runs/progress` отправляется каждые 10 секунд во время выполнения. В очередь не ставится.

```json
{
  "run_id": "uuid", "phase": "copy", "percent": 37.5,
  "files_done": 1200, "files_total": 3200, "bytes_done": 104857600, "bytes_total": 279620266,
  "speed_bps": 52428800, "eta_s": 210, "current_file": "D:\\Data\\reports\\2026-10.pdf"
}
```

`phase`: `pre_events`, `vss`, `scan`, `copy`, `verify`, `retention`, `post_events`.

`POST /api/v1/agent/runs/finish`:

```json
{
  "run_id": "uuid", "task_id": "uuid", "status": "warning",
  "finished_at": "2026-10-12T21:04:40Z",
  "source_files": 3200, "source_bytes": 279620266,
  "files_processed": 3197, "bytes_written": 98112000,
  "errors": 0, "warnings": 3,
  "error_message": null,
  "destinations": [
    { "destination_id": "uuid", "status": "success", "set_name": "Documents 2026-10-12 21-00 (Incremental)", "bytes": 98112000, "error": null }
  ],
  "verify": { "performed": true, "ok": true, "scope": "new", "sets_checked": 1, "failed_sets": [] },
  "retention": { "deleted_sets": 1 },
  "log_tail": "последние 100 строк журнала",
  "log_gz_b64": "есть только при status warning или error"
}
```

- `status`: `success`, `warning` (выполнено, но часть файлов пропущена), `error` или `aborted` (остановлено пользователем или командой).
- `source_files` и `source_bytes` описывают весь источник на момент запуска, даже при инкрементальной копии: по ним сервер ищет аномалии.
- `verify.scope`: `new` (проверена только что созданная копия) или `stored` (плановая проверка всех хранящихся наборов). Если какой-то набор не прошёл проверку, его имя попадает в `failed_sets`, а статус запуска становится `error` с `error_message` вида «Повреждён набор …».
- `start` и `finish` идемпотентны по `run_id`. При недоступности сервера они сохраняются в локальной очереди агента и отправляются позже строго по порядку.

### A.6. Снимок конфигурации

`POST /api/v1/agent/config` отправляется через 10 секунд после последнего локального изменения и по запросу `want_config`.

```json
{
  "config_revision": 43,
  "changed": [ { "task_id": "uuid", "revision": 8, "updated_by": "local:OFFICE\\user1", "updated_at": "..." } ],
  "settings": { "...": "объект A.9" },
  "credentials": [ { "id": "uuid", "kind": "windows", "user": "backup1", "domain": ".", "has_secret": true } ],
  "tasks": [ "объекты A.9 без секретов" ],
  "deleted_task_ids": [],
  "overwritten": [ "перезаписанные версии заданий (A.4), если были" ]
}
```

`updated_by` имеет вид `local:<ДОМЕН\пользователь>` для правок в программе или `server:<логин>` для правок с сайта. Правки `local:` сайт показывает ненавязчивым уведомлением.

### A.7. Журнал по запросу

`POST /api/v1/agent/runs/{run_id}/log` с телом `{"log_gz_b64": "..."}`. Это ответ на команду `log.fetch`. Если журнал уже удалён по сроку хранения, команда завершается `failed`.

### A.8. Инвентаризация хранилищ

`POST /api/v1/agent/inventory` отправляется после каждого запуска, раз в 6 часов и по команде.

```json
{
  "destinations": [
    {
      "task_id": "uuid", "destination_id": "uuid", "kind": "unc", "path": "\\\\fileserver\\docs",
      "total_bytes": 4000000000000, "free_bytes": 1250000000000,
      "sets": [ { "name": "Documents 2026-10-12 00-30 (Full)", "type": "full", "time": "2026-10-11T21:30:00Z", "bytes": 5100000000, "verified_at": "2026-10-12T21:10:00Z", "verify_ok": true } ]
```

Для FTP, WebDAV и S3 поля `total_bytes` и `free_bytes` могут быть `null`. Если набор ещё не проверялся, `verified_at` и `verify_ok` равны `null`.

### A.9. Объекты: задание, учётные данные, настройки

**Задание** (`task`). Значения по умолчанию указаны в комментариях. Неизвестные поля обе стороны сохраняют и не удаляют: это защита от расхождения версий.

```jsonc
{
  "id": "uuid",
  "revision": 7,
  "updated_at": "2026-10-12T10:00:00Z",
  "updated_by": "local:OFFICE\\admin",
  "name": "Documents",
  "enabled": true,
  "comment": "",
  "priority": 0,                       // больше = раньше в очереди
  "backup_type": "incremental",        // full | incremental | differential | mirror
  "mirror_mode": null,                 // exact | safe, только для mirror
  "force_full": { "every_runs": 0, "weekday": null, "month_day": null },  // weekday 1–7 (ISO, 1 = пн), month_day 1–31 или -1 = последний день
  "sources": [
    { "id": "uuid", "kind": "folder", "path": "D:\\Data", "credential_id": null, "recursive": true }
  ],                                   // kind: folder | file | unc
  "filters": {
    "include": [], "exclude": ["*.tmp", "~$*"], "exclude_dirs": ["Temp"],
    "skip_hidden": false, "skip_system": true, "skip_temp": true
  },
  "profile_sid": null,                 // чей профиль для %USERPROFILE% и т.п.; null = кто создал задание
  "destinations": [
    {
      "id": "uuid", "kind": "unc",     // local | unc | usb | ftp | ftps | sftp | s3 | webdav
      "path": "\\\\fileserver\\docs",
      "usb_label": null,               // для usb: метка тома; path тогда относительный
      "host": null, "port": null,      // ftp/ftps/sftp/webdav

    }

  "layout": {
    "separate_folders": true,          // «Отдельная папка для каждой копии»

    "encrypt_names": false,            // только 7z
    "password_credential_id": null
  },

    "every_runs": 0,                   // проверка новой копии: 0 = нет, 1 = каждый раз, N = каждый N-й запуск

  },
  "retention": {
    "mode": "count",                   // none | count | age | gfs
    "keep_full": 12,                   // для count
    "max_age_days": 0,                 // для age
    "gfs": { "daily": 7, "weekly": 4, "monthly": 12 },
```

**Учётные данные** хранятся отдельно, задания ссылаются на них по `credential_id`. Одну учётку можно использовать в нескольких заданиях.



### A.10. Обновления агента

Команда `update.install` несёт `version`, `sha256` пакета и `signature`: подпись сервера (A.2) строки `"{version}\n{sha256}"`. Агент скачивает пакет `GET /api/v1/agent/updates/{version}` (запрос подписан как обычно), проверяет SHA-256 и подпись, затем устанавливает. Новую версию сервер видит по следующему heartbeat. Пакет — zip с файлами программы и `manifest.json` (`version`, `min_protocol`, список файлов).

### A.11. Ошибки

Тело ошибки: `{"error": "код", "message": "текст"}`.

| HTTP | `error` | Действие агента |
|---|---|---|
| 400 | `bad_request` | Записать в журнал, не повторять |
| 401 | `bad_signature`, `clock_skew` | При `clock_skew` в теле есть `server_time`: записать «расходится время» |
| 403 | `pending`, `disabled`, `bad_registration_key` | Ждать, отчёты держать в очереди |
| 404 | `unknown_agent` | Зарегистрироваться заново (A.3) |
| 413 | `too_large` | Отправить без `log_gz_b64` |
| 429 | `rate_limited` | Ждать столько, сколько указано в `Retry-After` |
| 5xx / нет связи | — | Повторять через 1, 2, 5, 10, 10… минут |

### A.12. Статусы (общий словарь)

| Код | Где | Русское название | Смысл |
|---|---|---|---|
| `success` | запуск | Успешно | Всё скопировано |
| `warning` | запуск | С предупреждениями | Выполнено, часть файлов пропущена |
| `error` | запуск | Ошибка | Копия не создана или создана не полностью |
| `aborted` | запуск | Прервано | Остановлено вручную или командой |
| `running` | задание | Выполняется | Есть активный запуск |
| `missed` | задание | Пропущено | Слот расписания прошёл, машина была на связи, а запуска не было. **Это проблема** |
| `missed_offline` | задание | Пропущено, машина выключена | Слот прошёл, когда машина была не на связи. Не проблема, ждём догоняющий запуск |
| `stale` | задание | Давно нет успешной копии | Последняя успешная копия старше N дней (по умолчанию 7). Мягкая пометка |
| `online` / `offline` | агент | На связи / Не на связи | `offline`: нет heartbeat дольше N минут (по умолчанию 60). Само по себе не проблема |
| `pending` | агент | Ожидает подтверждения | Зарегистрирован, но не подтверждён |
| `disabled` | агент или задание | Отключено | — |
