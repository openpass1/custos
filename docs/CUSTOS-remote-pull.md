# CUSTOS — забор копий с удалённых Linux-серверов. Техническое задание

Версия ТЗ: 1.0 от 10.11.2026. Дополнение к [`CUSTOS-client.md`](CUSTOS-client.md) (клиент) и [`CUSTOS-monitor.md`](CUSTOS-monitor.md) (мониторинг). Общий контракт — [`protocol.md`](protocol.md); ссылки вида «A.9» ведут туда.

## 0. Как работать с этим документом

- Правила те же, что в разделе 0 ТЗ клиента: файлы целиком, точные команды, список проверки после каждого этапа. Общение на русском; код, комментарии и коммиты на английском.
- Новый компонент — **`custos-helper`**, скрипт на bash для Linux-сервера. Он лежит в репозитории в папке `helper/`.
- **Проверять только на тестовом сервере** (VPS или виртуальная машина с Linux), не на рабочем. Восстановление — тоже на тестовом сервере.
- Правки протокола (A.5, A.9) вносятся в `protocol.md` и его журнал A.13 вместе с реализацией этапа 2а, а не раньше.
- В репозиторий и материалы не попадают настоящие адреса, домены и имена учётных записей. Примеры: `vps.example.org`, `203.0.113.10`, `site_db`.

## 1. Что делаем

Сайты работают на VPS у хостера. Встроенный бэкап панели (ispmanager) пишет в одно хранилище того же хостера. Если инфраструктуру хостера взломают или уничтожат, пропадут и сервер, и его бэкапы. Второй бэкап «с сервера в облако» не спасает от взлома: ключи от облака лежат на сервере, и атакующий с root удалит копию.

Решение — перевернуть направление. **Агент CUSTOS в офисе сам забирает данные с сервера по SSH** и сохраняет их обычной копией CUSTOS: 7z, шифрование, хранение по правилам задания, отчёт в мониторинг.

```
                  исходящее SSH-соединение (из офиса наружу)
 [VPS у хостера] <──────────────────────────────── [Агент CUSTOS в офисе]
  custos-helper                                           │
  (только чтение)                                         ├──> [NAS / хранилище копий]
                                                          └──> [Сервер мониторинга CUSTOS]
```

| Ситуация | Сервер сам отправляет в облако | Агент CUSTOS забирает |
|---|---|---|
| Хостер уничтожен | облачная копия жива | копия в офисе жива |
| Сервер взломан, у атакующего root | ключ от облака на сервере, копию можно удалить | сервер ничего не знает об офисе, копию не достать |
| Нужно открывать офис в интернет | нет | нет, только исходящий SSH |
| Утёк ключ агента | — | только чтение того, что разрешено в конфиге custos-helper, и только с IP офиса (если он задан) |

**Чего не обещаем.** Восстановление на новом сервере остаётся ручной работой: панель, пользователи, сайты, базы. Это последний рубеж на случай гибели хостера или взлома. Бэкапы самой панели стоит оставить: панель восстанавливает их быстрее.

## 2. Место в CUSTOS

Новый **тип источника** «Удалённый Linux-сервер (SSH)». Расписание, очередь, типы копий, `force_full`, 7z и шифрование, назначения, хранение, проверка копий и отчёты работают как у любого задания.

Ограничения задания с таким источником:

- источник в задании один, смешивать его с папками Windows нельзя;
- тип «Зеркало» недоступен;
- VSS, фильтры, `profile_sid` и `copy.preserve_acl` не применяются: что забирать, решает конфиг custos-helper;
- форматы: 7z (назначения local, unc, usb, sftp), ZIP с Zip64 (любые назначения) и «без сжатия» (папка набора с теми же файлами, без шифрования).

Главное требование клиента сохраняется: **никаких временных файлов**. Данные идут потоком SSH → архив → назначение.

Выполнять задание может любой агент; лучше тот, что работает круглосуточно. Очередь агента последовательная, поэтому долгий забор задерживает его остальные задания.

## 3. custos-helper

Всё, что CUSTOS ставит на сервер, названо по имени custos, чтобы не путать с другими программами: скрипт `custos-helper`, пользователь `custos`, папка конфига `/etc/custos`, файл sudo `/etc/sudoers.d/custos`, метка в журнале `custos-helper`. В тексте ниже он везде называется custos-helper.

### 3.1. Установка и доступ

- Скрипт `/usr/local/sbin/custos-helper` (0755, root), конфиг `/etc/custos/helper.conf` (0600, root).
- Отдельный пользователь `custos` с обычной оболочкой (`/bin/bash`): через неё sshd запускает принудительную команду. Пароль — `*` (`useradd --password '*'`): войти по паролю нельзя, а вход по ключу работает. С паролем по умолчанию `!` (заблокированная учётная запись) OpenSSH при `UsePAM no` отказывает и во входе по ключу.
- sudo только на custos-helper, файл `/etc/sudoers.d/custos` (0440). Перед установкой файл проверяется `visudo -cf`: испорченный файл в `sudoers.d` ломает sudo целиком, а с ним и ваш вход через `sudo -i`.

  ```
  Defaults:custos env_keep += "SSH_ORIGINAL_COMMAND"
  custos ALL=(root) NOPASSWD: /usr/local/sbin/custos-helper
  ```

- Ключ агента в `~custos/.ssh/authorized_keys`:

  ```
  command="sudo -n /usr/local/sbin/custos-helper",restrict,from="203.0.113.10" ssh-ed25519 AAAA... custos
  ```

  `restrict` запрещает терминал и пробросы. `from=` ставится, если у офиса статический внешний IP; без него ключ работает с любого адреса.
- `sshd_config` не меняется. `PermitRootLogin forced-commands-only` **не использовать**: так можно закрыть себе обычный вход root'ом. Если в `sshd_config` есть `AllowUsers` или `AllowGroups`, туда нужно добавить `custos`.
- На сервере нужны bash 4.4+ (нужны `shopt -s inherit_errexit` и пустые массивы при `set -u`), GNU find, GNU tar и gzip. Python не нужен. Системы на BusyBox (Alpine) не поддерживаются.
- Каждый вызов пишется в syslog: `logger -t custos-helper` (операция, аргументы, код завершения).

### 3.2. Конфиг `helper.conf`

Одна настройка на строку, `ключ = значение`; строка, которая начинается с `#`, — комментарий. Списки задаются повтором ключа, поэтому пути могут содержать пробелы. custos-helper разбирает файл сам и **не выполняет его** (`source` запрещён).

```ini
# Пресет «ispmanager: только сайты»
root       = /var/www
root       = /etc/nginx
root       = /var/spool/cron/crontabs
exclude    = /var/www/*/data/logs
exclude    = /var/www/*/data/tmp
exclude    = /var/www/*/data/mod-tmp
exclude    = /var/www/httpd-logs
# СУБД: mariadb | mysql | postgresql, ключ можно повторить; нет строки — без баз
db_engine  = mariadb
# Пусто = вход root в MariaDB/MySQL через сокет, без пароля
db_defaults_file =
```

- `exclude` — шаблоны `find -path`: исключённая папка пропускается целиком, вместе с содержимым.
- `root` и `exclude` — только абсолютные пути; `root = /` запрещён. Корень, которого нет или который является символической ссылкой, пропускается с предупреждением (код 1), а не считается ошибкой конфига.
- Неизвестный ключ — ошибка конфига (код 78). Файл `helper.conf` должен принадлежать root и не быть доступным на запись группе и остальным, иначе тоже 78.
- Корни не должны вкладываться друг в друга (например, `/etc` и `/etc/nginx`): файлы попали бы в выборку дважды. Мастер не даёт сохранить такой список.
- Пресеты (что забирать — выбирается в мастере, см. 4.2):
  - **«ispmanager: только сайты»** (по умолчанию, конфиг выше) — чтобы перенести сайты на любой сервер или панель: файлы сайтов (SSL-сертификаты ispmanager тоже лежат в `/var/www`, в `httpd-cert`), базы, а для справки — настройки nginx и задания cron. Логи веб-сервера (`/var/www/httpd-logs`) и временные папки сайтов исключены: для переноса они не нужны, а живой лог давал бы предупреждение «file changed as we read it» при каждом заборе. Если сайты работают и через Apache, в список добавляется `root = /etc/apache2`.
  - **«ispmanager: сайты и панель»** — чтобы поднять тот же сервер с ispmanager целиком: `root` = `/var/www`, `/etc`, `/usr/local/mgr5/etc`, `/var/spool/cron/crontabs`, исключения и базы те же. Весь `/etc` содержит хеши паролей и закрытые ключи SSH сервера, поэтому мастер при выборе этого варианта предупреждает, что они окажутся в копиях.
  - **«Обычный Linux»** — сервер без панели: `root` = `/etc`, `/home`, `/root`, `/var/www`, `/var/spool/cron`; базы — все, кроме системных. Предупреждение про `/etc` то же.
- `db_engine` можно указать дважды, если на сервере две СУБД: `mariadb` или `mysql` плюс `postgresql`. `mariadb` и `mysql` вместе указать нельзя.
- Системные базы custos-helper пропускает сам: `information_schema`, `performance_schema`, `sys` и `mysql` у MariaDB и MySQL (пользователи и права всё равно попадают в копию через `db-users`), `template0` и `template1` у PostgreSQL. В `db_exclude` пишут только свои исключения, по одному имени на строку.
- Если root не входит в MariaDB или MySQL без пароля, `db_defaults_file` указывает на файл вида `my.cnf` (0600) с учётной записью. Лучше отдельный пользователь СУБД только на чтение: `SELECT`, `SHOW VIEW`, `TRIGGER`, `EVENT`, `LOCK TABLES`, `PROCESS`.
- PostgreSQL: custos-helper входит через локальный сокет от системного пользователя `postgres` (`runuser -u postgres --`), пароль не нужен.
- Конфиг на сервере — граница безопасности: агент получает только то, что в нём разрешено, и расширить это не может.

### 3.3. Операции

Агент передаёт операцию обычной SSH-командой (`ssh custos@vps.example.org db-dump mariadb site_db`). custos-helper читает её из `SSH_ORIGINAL_COMMAND`. Вся строка должна состоять из символов `[A-Za-z0-9_$ -]`, иначе отказ с кодом 64 (так отсекаются переводы строк и спецсимволы shell); затем она делится по пробелам, и принимаются только операции из таблицы. Для проверки на месте root может передать операцию аргументами (`custos-helper info`) — с тем же белым списком. `<СУБД>` — `mariadb`, `mysql` или `postgresql`, и она должна быть указана в конфиге.

| Операция | Что возвращает |
|---|---|
| `info` | JSON: версия custos-helper, номер протокола custos-helper, имя хоста, ОС, текущее время сервера (Unix-секунды), SHA-256 конфига, СУБД, корни и свободное место на их дисках |
| `db-list <СУБД>` | имена баз по одному на строку: все базы этой СУБД, кроме системных и `db_exclude` |
| `db-dump <СУБД> <имя>` | SQL-дамп одной базы потоком |
| `db-users <СУБД>` | пользователи (роли) и права этой СУБД в виде SQL |
| `manifest` | список всего, что лежит в корнях, сжатый gzip |
| `tar-since <время> [<КБ/с>]` | tar (pax) всех папок и тех файлов, у которых ctime новее `<время>`; `0` — полная копия; второй аргумент ограничивает скорость |

К `db-dump`, `db-users` и `tar-since` можно добавить последним словом `gzip` (`db-dump mariadb site_db gzip`, `tar-since 0 gzip`, `tar-since 0 1000 gzip`): поток тогда сжимается `gzip -6 -n` прямо на сервере. Агент всегда просит `gzip` и распаковывает поток на лету. Проверено на сервере с ispmanager (11.11.2026): файлы сайтов сжимаются в 1,7 раза, и полная копия идёт вдвое быстрее, а дампы — обычный текст и сжимаются в разы. `gzip` есть на любом сервере, а агенту хватает встроенного в .NET `GZipStream`. zstd сжимал бы ещё примерно на 10% лучше, но его нет на каждом сервере, а агенту понадобилась бы отдельная библиотека.

Пример ответа `info`:

```json
{
  "helper_version": "1.0.0", "protocol": 1,
  "hostname": "vps", "os": "Ubuntu 24.04 LTS", "now": 1794328800,
  "config_sha256": "9f2c…", "db_engines": ["mariadb"],
  "roots": [ { "path": "/var/www", "free_bytes": 52000000000 } ]
}
```

**`db-dump`**. Дамп не сжимается: 7z сожмёт его лучше.
- MariaDB и MySQL: `mariadb-dump` (или `mysqldump` для MySQL) с параметрами `--single-transaction --quick --routines --triggers --events --hex-blob --default-character-set=utf8mb4` (старый `mysqldump` по умолчанию берёт трёхбайтовую `utf8`). Согласованность гарантируется только для таблиц InnoDB; таблицы MyISAM снимаются как есть.
- PostgreSQL: `pg_dump --no-password` в обычном текстовом формате; дамп всегда согласован.

**`db-users`**:
- MariaDB: `mariadb-dump --system=users --insert-ignore`: пишет `CREATE USER IF NOT EXISTS`, иначе восстановление остановится на уже существующем `root@localhost`.
- MySQL: такого параметра нет, поэтому custos-helper выгружает `SHOW CREATE USER` и `SHOW GRANTS` по каждой несистемной учётной записи и пишет их как `CREATE USER IF NOT EXISTS …`. Нужен MySQL 8.0.17+ (`print_identified_with_as_hex`). В конце — строка `-- Dump completed on …`, как у `mariadb-dump`.
- PostgreSQL: `pg_dumpall --globals-only --no-password` (роли с хешами паролей и табличные пространства).

**`manifest`**: одна запись на файл, папку или ссылку; 11 полей, каждое заканчивается байтом NUL:

```
find <корни> \( <исключения> \) -prune -o -printf '%y\0%s\0%T@\0%C@\0%m\0%U\0%G\0%u\0%g\0%l\0%p\0'
```

Поля: тип, размер, mtime, ctime, права (восьмеричные), uid, gid, имя владельца, имя группы, цель ссылки, путь. Формат с NUL выбран потому, что в именах файлов бывают табуляции и переводы строк; собирать из них JSON в bash ненадёжно.

**`tar-since`**: тот же обход `find`, что и для `manifest`, с отбором `\( -type d -o -newerct @<время> \)`, передаётся в

```
tar --create --file=- --format=pax --null --no-recursion --files-from=- --ignore-failed-read \
    --pax-option=exthdr.name=%d/PaxHeaders/%f,delete=atime
```

- `find` запускается из `/`, поэтому имена в tar относительные (`var/www/…`), без предупреждения «Removing leading /»; архивы восстановления тоже не пишут по абсолютным путям. В `manifest` пути остаются абсолютными.
- `--pax-option` делает поток повторяемым: одни и те же файлы дают байт в байт одинаковый tar (иначе tar 1.34 вписывает PID в имена заголовков, а atime меняется при каждом чтении).
- Сокеты пропускаются и в `manifest`, и в tar: ispmanager держит сокеты php-fpm в `/var/www/php-fpm`, и tar писал бы «socket ignored» при каждом запуске.

- Пути custos-helper берёт только из своего обхода. **Путей от агента он не принимает**, поэтому проверять их не нужно, и через символическую ссылку в середине пути выйти за корень нельзя.
- `find` не переходит по символическим ссылкам; в tar попадает сама ссылка.
- ctime меняется при любой правке содержимого, прав и владельца, при переименовании и переносе, и выставить его вручную нельзя. Поэтому в выборку попадают и файлы, которым вернули старую дату изменения (проверено на GNU find 4.9 и tar 1.35).
- Папки входят в каждую копию: так сохраняются их права и владельцы.
- Ограничение скорости: `--checkpoint=<N> --checkpoint-action=sleep=1`, где N рассчитывается из заданных КБ/с (одна запись tar — 10 КБ). Дампы не ограничиваются. С `gzip` ограничение действует на данные до сжатия, так что по сети идёт меньше заданного.
- С `gzip` код завершения тот же, что без него: ошибка дампа или tar не теряется за успешным gzip.
- Коды завершения `manifest` и `tar-since`: 0 — успех; 1 — предупреждение: файл изменился или исчез во время чтения, пропущен корень, вообще что-либо записано в stderr; 2 и больше — ошибка. Код самого tar для этого недостаточен: с `--ignore-failed-read` файл, исчезнувший между `find` и tar, даёт код 0.

### 3.4. Требования к коду

- `set -euo pipefail`, `export LC_ALL=C`. Никакого `eval`, `source` конфига и подстановки аргументов в строку для shell.
- Белый список операций и числа аргументов. На всё остальное — отказ.
- `<время>` и `<КБ/с>` — только цифры. `<СУБД>` — одна из указанных в конфиге. Имя базы для `db-dump` должно быть в текущем `db-list` этой СУБД, состоять из `[A-Za-z0-9_$-]` и не начинаться с `-`. Базы с другими именами `db-list` не выводит, а пишет о них в stderr.
- custos-helper ничего не пишет на диск, кроме записи в syslog.
- Коды завершения: код основной команды (дамп, tar), 64 — неверный вызов, 78 — ошибка конфига. Сообщения — в stderr, текстом.
- Скрипт маленький и читаемый (ориентир — до 250 строк), без замечаний ShellCheck, с номером версии в начале.
- Тесты в GitHub Actions на Linux: настоящие OpenSSH, MariaDB, MySQL и PostgreSQL в Docker; проверки отказов, имён с пробелами и переводами строк, ссылок, исключений, выборки по ctime, кодов завершения.

## 4. Изменения в клиенте

### 4.1. Источник в задании (A.9)

```jsonc
{
  "id": "uuid",
  "kind": "ssh",
  "host": "vps.example.org",
  "port": 22,
  "user": "custos",
  "credential_id": "uuid",             // учётные данные вида ssh_key
  "host_key_sha256": "SHA256:…",       // закреплённый отпечаток ключа сервера
  "preset": "ispmanager_sites",        // ispmanager_sites | ispmanager_full | linux; нужен только мастеру
  "office_ip": "203.0.113.10",         // для строки authorized_keys; null = без from=
  "speed_limit_kbps": 0                // 0 = без ограничения
}
```

- Новый вид учётных данных **`ssh_key`**: пару ключей ed25519 создаёт агент. Закрытый ключ хранится под DPAPI (SYSTEM) и никуда не уходит, ни в мониторинг, ни в журналы. Открытый ключ можно показывать.
- `host_key_sha256` меняется **только локально**, в мастере или редакторе задания, как адрес сервера мониторинга. Правки задания с сайта это поле сохраняют, но не меняют.

### 4.2. Мастер настройки

Мастер создаёт под сервер только настройки. Сам скрипт custos-helper одинаков для всех: его проверяют тесты при каждой сборке, и его можно сверить по SHA-256.

1. Адрес, порт (22), имя пользователя (`custos`; блок установки создаёт именно его, другое имя — только для сервера, настроенного вручную).
2. IP офиса — необязательное поле. Если оно пустое, мастер предупреждает, что ключ будет работать с любого адреса.
3. Что забирать (пресет, см. 3.2): «ispmanager: только сайты» (по умолчанию), «ispmanager: сайты и панель» или «Обычный Linux». Списки корней, исключений и исключённых баз и СУБД (MariaDB, MySQL, PostgreSQL) можно поправить; поправленные списки сохраняются как пресет `custom` («Свои списки»). Для вариантов с целым `/etc` мастер предупреждает, что в копии попадут хеши паролей и ключи SSH сервера.
4. CUSTOS создаёт ключ ed25519 и показывает **один блок для вставки** в сессию root на сервере (после `sudo -i`), с кнопками «Копировать» и «Сохранить как файл». Пример — в приложении.
5. «Проверить подключение»: мастер показывает отпечаток ключа сервера, админ подтверждает, отпечаток запоминается. Затем вызываются `info`, `db-list` и `manifest`: видно версию custos-helper, список баз, число файлов и объём.
6. Дальше — обычные страницы редактора: расписание, архив, назначения, хранение.

Сам ставить custos-helper на сервер мастер не будет: для этого CUSTOS пришлось бы получить логин и пароль sudo. Блок для вставки прозрачнее, в нём видно всё, что выполняется от root.

### 4.3. Ход запуска

1. **Подключение.** Ключ сервера сверяется с закреплённым. Не совпал — запуск `error` «Ключ сервера изменился», данные не читаются. Сервер недоступен — до трёх попыток с паузой в минуту, затем `error`.
2. **`info`.** Несовместимый протокол custos-helper — `error` с командой обновления. Устаревший, но совместимый custos-helper, а также изменившийся конфиг (другой `config_sha256`) дают предупреждение.
3. **Дампы.** Для каждой СУБД из `info`: `db-list`, затем `db-dump … gzip` по каждой базе и `db-users … gzip`, каждый распаковывается на лету и сразу идёт в архив. Дамп засчитывается, если код завершения 0 и в конце есть строка-признак: у MariaDB и MySQL последняя строка начинается с `-- Dump completed`; у PostgreSQL после строки `-- PostgreSQL database dump complete` (у `db-users` — `-- PostgreSQL database cluster dump complete`) допускаются только `--`, пустые строки и одна строка `\unrestrict …`: так заканчивают вывод `pg_dump` и `pg_dumpall` начиная с версий августа 2025 (13.22, 14.19, 15.14, 16.10, 17.6 и новее). Ошибка одной базы не останавливает остальные, но запуск получает `error`.
4. **`manifest`.** Сравнение с манифестом прошлой успешной копии: сколько файлов изменено и удалено, объём источника.
5. **`tar-since … gzip`.** Время отсчёта — `now` из `info` прошлой успешной копии минус 10 минут. Для полной копии — 0, для дифференциальной — время последней полной. Агент читает заголовки tar на лету, ничего не распаковывая: считает прогресс, SHA-256 каждого файла и запоминает, что реально попало в копию.
6. **Манифест** `custos-set.json` записывается в архив последним (у 7-Zip — первым, см. 4.4), набор закрывается и теряет суффикс `.partial`.
7. Хранение, проверка, отчёт — как у всех заданий.

Статусы:

- `success` — всё забрано;
- `warning` — файл исчез или изменился во время чтения, custos-helper устарел, конфиг изменился;
- `error` — не удался дамп хотя бы одной базы, сервер недоступен, ключ сервера изменился, tar завершился кодом 2 и больше, сработал предохранитель по памяти.

При `error` набор сохраняется, в манифесте он помечен `error` вместе со списком неудавшихся баз, а при восстановлении CUSTOS об этом предупреждает. Как и у остальных заданий, после ошибки хранение ничего не удаляет, а следующий запуск снова берёт изменения с последней успешной копии.

### 4.4. Состав набора

```
custos-set.json   манифест (раздел 7 ТЗ клиента) с полями для Linux
files.tar         все файлы (полная копия) или изменённые (инкрементальная, дифференциальная)
db/<СУБД>/<имя>.sql    дамп каждой базы (db/mariadb/site_db.sql)
db/<СУБД>/_users.sql   пользователи и права этой СУБД
```

- Такая же раскладка `db/` у дампов локальных баз на Windows (раздел 6.2 ТЗ клиента), поэтому восстановление дампов общее.
- Имя файла дампа — имя базы, в котором всё, кроме `A-Z a-z 0-9 _ . -`, заменено на `_`; при совпадении добавляется номер. Настоящее имя базы хранится в манифесте.
- Дополнения к `custos-set.json`, все необязательные:
  - в заголовке: `source_kind: "ssh"`; блок `remote` с хостом, версией custos-helper, временем сервера, `config_sha256` и временем отсчёта; список баз (`engine`, `name`, `file`, `bytes`, `ok`);
  - у файлов: `type`, `mode`, `uid`, `gid`, `user`, `group`, `link`, `ctime`. Путь — абсолютный путь Linux; если имя не в UTF-8, вместо `path` пишется `path_b64`.
- Порядок записи. В ZIP и в наборе без архива идут дампы, затем `files.tar`, затем `custos-set.json`: манифест пишется, когда tar уже прочитан, и точно знает, какие файлы в него попали и их SHA-256. 7-Zip кладёт элементы по именам, и манифест у него идёт первым: в нём перечислено, что попадёт в tar, по `ctime` каждой записи, а SHA-256 файлов нет. Восстановление в обоих случаях берёт содержимое из самого tar, а хеши, если они есть, проверяет.
- Пути в задании такого типа сравниваются **с учётом регистра** (`Logo.png` и `logo.png` — разные файлы). У заданий Windows сравнение остаётся без учёта регистра.

### 4.5. Восстановление

- То же окно, что в 6.11 ТЗ клиента: задание или папка назначения → дата → локальная папка для результата. Восстанавливать может только администратор. «На исходное место» для такого набора недоступно: окно само выбирает «В другую папку».
- Результат:
  - отдельный tar на каждый корень (`var-www.tar`, `etc-nginx.tar`, `var-spool-cron-crontabs.tar` …) с последней версией каждого файла на выбранную дату; удалённые к этой дате файлы не попадают. Имя tar — путь корня, где `/` заменены на `-`, а всё, кроме `A-Z a-z 0-9 _ . -`, — на `_`. Записи вне нынешних корней (корни поменяли между копиями) попадают в `other.tar`;
  - папка `db/` с дампами и `_users.sql` по каждой СУБД;
  - `README.txt` с командами.
- Архивы собираются **копированием блоков tar как есть**, без переупаковки: так сохраняется всё, что записал GNU tar, включая владельцев и необычные имена.
- Наборы цепочки читаются от выбранного к полному. Каждая запись берётся один раз, из самого нового набора, где она есть; список того, что должно быть на эту дату, — манифест выбранного набора. SHA-256 файла сверяется с манифестом его набора: при расхождении файл вырезается из результата, а восстановление получает `error`. Записи, которых не нашлось ни в одном наборе, перечисляются в журнале (первые 20 по имени).
- «Существующие файлы: пропускать» относится к tar целиком: tar, который уже есть в папке, не перезаписывается.
- В `README.txt` (UTF-8 без BOM, строки с LF: его читают на сервере) прямо сказано: корни с настройками поверх нового сервера не распаковывать, это затрёт его настройки, а целый `/etc` (пресеты «ispmanager: сайты и панель» и «Обычный Linux») — ещё и сеть, `fstab`, пользователей и ключи SSH. Корни с настройками — `/etc`, всё внутри него и папки `etc` в других местах (`/usr/local/mgr5/etc`). Их распаковывают в отдельную папку и берут оттуда нужное. Команды в `README.txt` выглядят так (от root на сервере, в папке с результатом):

  ```bash
  tar -xpf var-www.tar -C /                                          # файлы сайтов на место
  mkdir -p /root/old-etc && tar -xpf etc-nginx.tar -C /root/old-etc  # настройки — только в отдельную папку
  mariadb < db/mariadb/_users.sql                                    # пользователи и права
  mariadb -e 'CREATE DATABASE IF NOT EXISTS `site_db`'
  mariadb site_db < db/mariadb/site_db.sql
  sudo -u postgres psql -d postgres < db/postgresql/_users.sql       # PostgreSQL
  sudo -u postgres createdb site_db
  sudo -u postgres psql -d site_db < db/postgresql/site_db.sql
  ```

  Дампы PostgreSQL новых версий содержат команды `\restrict` и `\unrestrict`, поэтому загружать их нужно `psql` не старее августа 2025 (см. версии в 4.3).

- Автоматического восстановления на сервер нет: для него нужен ключ с правом записи.

### 4.6. Безопасность на стороне агента

- Всё, что приходит с сервера, — недоверенные данные: взломанный сервер может прислать испорченный tar, странные имена баз или огромный ответ, а агент работает от SYSTEM в офисе. Поэтому:
  - tar на Windows не распаковывается никогда;
  - имена баз превращаются в безопасные имена файлов (4.4);
  - размеры ответов ограничены: `info` — 64 КБ, `db-list` — 10 000 имён;
  - разбор JSON — только System.Text.Json.
- **Предохранитель по памяти.** SSH.NET принимает данные из сети сразу, даже если архив не успевает их сжимать, и копит излишек в памяти без предела (проверено по исходникам версии 2026.0.0). Если непрочитанный хвост больше 256 МБ, запуск прерывается с `error` и советом включить ограничение скорости. Хвост — длина `OutputStream` команды SSH.NET: это ровно то, что принято из сети и ещё не прочитано (проверено прототипом в начале этапа 2а).

### 4.7. Библиотеки

- **SSH.NET** 2026.0.0 или новее (MIT, есть сборка под .NET 10): ключи ed25519, проверка ключа сервера (`HostKeyReceived`, SHA-256), `KeepAliveInterval`, потоковое чтение stdout и stderr, код завершения.
- Генерация ключей — **BouncyCastle.Cryptography** (MIT): приходит вместе с SSH.NET.
- Чтение заголовков tar — свой небольшой разборщик ustar и pax либо `System.Formats.Tar`. Сборка архивов восстановления — копированием блоков.
- Обе библиотеки вносятся в `THIRD-PARTY-NOTICES.txt`.

## 5. Изменения в мониторинге и протоколе

Задания с источником `ssh` — **обычные задания**. Слоты, пропуски, проблемы, аномалии и уведомления работают без изменений. Ошибка дампа, недоступность сервера и смена его ключа дают запуск `error` с понятным `error_message`, а значит обычную проблему и уведомление. Новых видов проблем нет.

Правки протокола, все только добавляющие (вносятся в `protocol.md` и A.13 вместе с этапом 2а; версия протокола остаётся 1 до первого релиза):

- A.9: источник вида `ssh` с полями из 4.1 и учётные данные вида `ssh_key`.
- A.5, `runs/finish`: необязательный блок `remote` и необязательный список `databases`. Список общий: он же приходит от заданий с дампами локальных баз на Windows (6.2 ТЗ клиента) и вносится в протокол с тем этапом, который будет сделан первым.

  ```json
  "remote": {
    "helper_version": "1.0.0", "server_free_bytes": 52000000000,
    "files_changed": 120, "files_deleted": 3
  },
  "databases": [ { "engine": "mariadb", "name": "site_db", "bytes": 10485760, "ok": true } ]
  ```

- `source_files` и `source_bytes` — файлы в корнях плюс дампы. По ним работает поиск аномалий (6.5 ТЗ мониторинга).

На сайте источник показывается как «Linux-сервер vps.example.org», блок `remote` — на странице запуска.

## 6. Безопасность — сводка

- Только чтение заложено в схему: принудительная команда, `restrict`, `from=` (если IP статический), sudo только на custos-helper, белый список операций, никаких путей от агента.
- Ключ агента читает всё, что разрешено в конфиге: файлы сайтов с паролями баз, дампы и остальные корни. «Только чтение» не значит «безопасно», поэтому агент для таких заданий должен стоять на хорошо защищённой машине. Корни — только нужные: по умолчанию весь `/etc` не забирается, а в пресетах, где он есть, его можно сузить до нужных папок.
- Отдельный ключ на каждый сервер. Отпечаток ключа сервера закреплён; при смене — остановка и ошибка.
- Хранилище копий на NAS не должно быть доступно обычным пользователям, иначе до него доберётся шифровальщик в офисной сети.
- custos-helper пишет каждый вызов в syslog.

## 7. Этапы

**Этап H. custos-helper.** Можно делать в любой момент: от клиента он не зависит. Мастер этапа 2а сам скрипт не пишет, а только вставляет готовый и проверенный custos-helper в блок установки, поэтому этап H делается раньше.
- `helper/custos-helper`, `helper/README.md` (по-русски: установка вручную, проверка, удаление), тесты в GitHub Actions.
- *Итог:* custos-helper ставится на тестовый сервер, и дампы и файлы можно забрать вручную из командной строки Windows: `ssh -i ключ custos@vps.example.org db-dump mariadb site_db > site_db.sql` (в `cmd`, не в Windows PowerShell 5: он портит двоичный поток).

**Этап 2а клиента. Удалённые Linux-серверы.** Требует этап 2 клиента (архивы, шифрование, восстановление на дату) и этап H. Если этап 2б клиента (базы на Windows) сделан раньше, общая часть по базам берётся из него. Может идти до или после этапа 3; решается к концу этапа 2.
- Первый день — прототип: прогнать 10 ГБ через SSH.NET в намеренно медленный архив и посмотреть на память.
- Источник `ssh`, учётные данные `ssh_key`, мастер, ход запуска, состав набора, восстановление, предохранитель по памяти.
- Тесты `Custos.Core` на Linux против Docker-контейнера с OpenSSH, custos-helper, MariaDB и PostgreSQL.
- *Проверка:* полная и инкрементальная копия с тестового сервера; смена ключа сервера даёт ошибку; ошибка дампа даёт ошибку; учебное восстановление на чистый тестовый сервер.

**Мониторинг.** Блок `remote` и показ источника — вместе с этапом 3 клиента и этапом 3 сервера.

**Требование к этапу 2 клиента:** архиватор (7z и ZIP) принимает элементы из потока неизвестной длины, а не только файлы с диска.

## 8. Позже и не делаем

**Позже:**
- пресеты для других панелей;
- для всех заданий CUSTOS: аномалия «необычно большая доля изменённых файлов» (`files_processed / source_files`) и заморозка хранения при аномалии, чтобы старые чистые копии не вытеснялись испорченными;

**Не делаем:**
- забор только по SFTP без custos-helper: для дампов он требует cron на сервере, а там, где можно прописать ключ с принудительной командой, можно поставить и custos-helper;
- rsync;
- установку custos-helper мастером по паролю sudo;
- Windows-серверы как источник этого вида.

## Приложение. Пример блока установки

Блок целиком генерирует мастер; ниже — его вид для пресета «ispmanager: только сайты». Вставляется в сессию root (после `sudo -i`). Команды выполняются в отдельном `bash -e`: при ошибке он остановится, а ваша сессия останется открытой. Повторный запуск безопасен.

```bash
bash -e <<'CUSTOS_INSTALL_EOF'
id custos >/dev/null 2>&1 || useradd --system --create-home --shell /bin/bash --password '*' custos

# 1. custos-helper (текст скрипта мастер вставляет целиком) и проверка контрольной суммы
cat > /usr/local/sbin/custos-helper.new <<'CUSTOS_HELPER_EOF'
#!/bin/bash
# … текст custos-helper …
CUSTOS_HELPER_EOF
echo "<sha256>  /usr/local/sbin/custos-helper.new" | sha256sum -c -
install -m 0755 /usr/local/sbin/custos-helper.new /usr/local/sbin/custos-helper
rm /usr/local/sbin/custos-helper.new

# 2. Конфиг
install -d -m 0755 /etc/custos
cat > /etc/custos/helper.conf <<'CUSTOS_CONF_EOF'
root       = /var/www
root       = /etc/nginx
root       = /var/spool/cron/crontabs
exclude    = /var/www/*/data/logs
exclude    = /var/www/*/data/tmp
exclude    = /var/www/*/data/mod-tmp
exclude    = /var/www/httpd-logs
db_engine  = mariadb
CUSTOS_CONF_EOF
chmod 0600 /etc/custos/helper.conf

# 3. sudo только на custos-helper. Файл сначала проверяется visudo: sudo пропускает файлы
#    с точкой в имени, поэтому черновик custos.new ни на что не влияет, а испорченный
#    файл не попадёт на место и не сломает sudo.
cat > /etc/sudoers.d/custos.new <<'CUSTOS_SUDO_EOF'
Defaults:custos env_keep += "SSH_ORIGINAL_COMMAND"
custos ALL=(root) NOPASSWD: /usr/local/sbin/custos-helper
CUSTOS_SUDO_EOF
chmod 0440 /etc/sudoers.d/custos.new
visudo -cf /etc/sudoers.d/custos.new
mv /etc/sudoers.d/custos.new /etc/sudoers.d/custos

# 4. Ключ агента
KEY_LINE='command="sudo -n /usr/local/sbin/custos-helper",restrict,from="203.0.113.10" ssh-ed25519 AAAA... custos'
install -d -m 0700 ~custos/.ssh
touch ~custos/.ssh/authorized_keys
grep -qxF "$KEY_LINE" ~custos/.ssh/authorized_keys || echo "$KEY_LINE" >> ~custos/.ssh/authorized_keys
chmod 0600 ~custos/.ssh/authorized_keys
chown -R custos: ~custos/.ssh

echo 'OK: custos-helper установлен'
CUSTOS_INSTALL_EOF
```
