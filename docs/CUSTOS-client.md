# CUSTOS — клиент для Windows. Техническое задание

Версия ТЗ: 1.0 от 12.10.2026. Второй документ проекта — `CUSTOS-monitor.md` (сервер мониторинга на PHP). Общий контракт между ними вынесен в приложение A, оно одинаково в обоих файлах.

## 0. Как работать с этим документом

- **Заказчик и тестировщик** — системный администратор, не программист. Он собирает и запускает программу на Windows, присылает журналы, скриншоты и тексты ошибок.
- **Как отдавать код.** Файлы целиком, а не фрагменты вида «вставьте это после строки N». После каждого шага: точные команды сборки и короткий список, что проверить руками.
- **Язык.** Общение на русском. Код, комментарии, имена, сообщения коммитов — на английском: проект будет опубликован на GitHub под лицензией **GPL-3.0**. Интерфейс программы на русском и английском.
- **Порядок.** Работаем по этапам из раздела 12. Каждый этап должен собираться и быть пригоден к реальной проверке.
- **Если решение в ТЗ не работает** (библиотека не поддерживает .NET 10, Windows ведёт себя иначе), предложить замену и объяснить, на что она влияет. Не обходить молча.
- **Тестировать** на отдельной виртуальной машине и тестовой шаре. Хранение и удаление старых копий никогда не проверять на настоящих бэкапах.

## 1. Что делаем

**CUSTOS** (лат. «хранитель»; Collect, Unify, Store, Track, Oversee, Secure) — программа резервного копирования файлов для Windows на замену устаревшему Cobian Backup 11. Работает полностью автономно, а при наличии сервера мониторинга (`CUSTOS-monitor.md`) отчитывается ему и принимает от него задания.

- Платформы: Windows 10 и 11, Windows Server 2019, 2022 и 2025. Только x64.
- Масштаб: у автора около 20 машин. Проект рассчитан на сотни агентов на один сервер.
- Главное требование: **копия пишется сразу в место назначения**, без промежуточной локальной копии. Временные файлы на локальном диске не создаются, SSD не изнашивается.

## 3. Архитектура

### 3.1. Процессы

- **`CustosService`** — служба Windows от LocalSystem. В ней всё главное: расписание, очередь, выполнение заданий, VSS, учётные данные, база, связь с сервером, обновление.
- **`Custos.exe`** — интерфейс с иконкой в трее. Запускается **в каждом пользовательском сеансе независимо**: в отличие от Cobian, новый экземпляр не закрывает интерфейс в других сеансах. В пределах одного сеанса работает один экземпляр (мьютекс `Local\`). Интерфейс ничего не выполняет сам, он только показывает состояние службы и передаёт ей команды.
- **`Custos.Updater.exe`** — маленькая программа обновления: останавливает службу, заменяет файлы, запускает службу.
- **`Custos.Core`** — общая библиотека: модели (приложение A.9), протокол, общий код.

### 3.2. Связь интерфейса и службы

- Именованный канал `\\.\pipe\custos`, сообщения JSON (запрос-ответ плюс поток событий от службы).
- Служба рассылает всем подключённым интерфейсам события: прогресс, строки журнала, смену статусов.
- **Служба сама проверяет права** вызывающего, интерфейсу не доверяет. Личность клиента канала определяется через impersonation (`NamedPipeServerStream.RunAsClient`). Правила — в разделе 4.

### 3.3. Файлы и папки

```
C:\Program Files\CUSTOS\           программа, 7z.dll, Updater
C:\ProgramData\CUSTOS\
    config\settings.json           настройки (A.9)
    config\tasks.json              задания (A.9)
    config\credentials.json        учётные данные; секреты под DPAPI (SYSTEM)
    config\agent.key               ключ агента (A.2), под DPAPI
    db\custos.db                   SQLite: индекс файлов, история, очередь отчётов
    logs\                          журналы службы и запусков
```

Папка `config` закрыта ACL: доступ только у SYSTEM и Administrators. Без этого ограничение «задания меняют только администраторы» обходится правкой файла. Пароли шифруются DPAPI в контексте SYSTEM, поэтому даже скопированный файл бесполезен на другой машине.

## 4. Права доступа

Служба работает от SYSTEM, а значит **право менять задания равносильно правам администратора**: можно вписать скрипт в событие, указать источником чужой профиль или системные файлы и забрать их через VSS. Отсюда правила:

| Действие | Кто может (по умолчанию) |
|---|---|
| Смотреть список заданий, статус, прогресс, журнал, историю | Все |
| Запускать, останавливать, ставить на паузу | Все |
| Создавать, менять, клонировать, удалять задания; менять настройки | Только администраторы |
| Восстанавливать копии | Только администраторы |

- **Администратор** — пользователь, в токене которого есть SID `BUILTIN\Administrators`, в том числе как deny-only (UAC-фильтрованный токен). Тогда администратору не нужно запускать программу «от имени администратора».
- Настройка **«Разрешить всем пользователям менять задания»**, по умолчанию выключена. При включении показывать предупреждение о том, что это фактически даёт права администратора.
- **Пароль программы** (необязательный). Если он задан, изменения и восстановление требуют ввода пароля в дополнение к правам. После ввода интерфейс остаётся разблокированным 30 минут или до закрытия. Хранится как хэш (A.2). Задаётся локально или с сервера (`settings.update`).
- **Режим иконки в трее** для обычных пользователей (задаёт администратор):
  - `full` — по умолчанию: весь интерфейс, а изменения по правам выше;
  - `status` — только иконка со статусом и окно состояния;
  - `hidden` — иконки нет.

  Администраторы всегда видят полный интерфейс.
- Любая локальная правка задания записывает `updated_by = local:ДОМЕН\пользователь` и отправляется на сервер (A.6). Там она отображается ненавязчивым уведомлением.

## 5. Интерфейс

- **Главное окно** в духе Cobian:
  - список заданий без групп: название, тип, расписание, последний запуск, результат, следующий запуск;
  - панель кнопок: создать, изменить, клонировать, удалить, запустить, остановить, пауза, восстановить;
  - внизу вкладки «Журнал» (в реальном времени, как в Cobian: что копируется, какие файлы не удались, почему задание не запустилось), «История запусков» и «Прогресс» (текущий файл, процент, скорость, оставшееся время).
- **Прогресс показывается только в окне программы**, не всплывающими окнами. Всплывающих уведомлений в трее нет.
- **Редактор задания** — вкладки слева, как в Cobian: Основное, Источники, Назначения, Расписание, Архив, Хранение, Фильтры, События, Дополнительно. У каждого непонятного параметра есть подсказка с объяснением.
- **Настройки программы**: язык (авто, русский, английский), тема (**авто по умолчанию**, светлая, тёмная), режим трея, права, пароль программы, срок хранения журналов, детальность журнала по умолчанию, приоритет, подключение к серверу (адрес, ключ регистрации, состояние, отпечатки ключей), «Разрешить серверу менять задания».
- **Меню иконки в трее**: открыть, запустить все задания, остановить текущее, закрыть интерфейс. Закрытие интерфейса службу не останавливает.
- Интерфейс автоматически запускается при входе любого пользователя (`HKLM\...\Run`).

## 6. Возможности задания

Формат задания — объект `task` из приложения A.9.

### 6.1. Типы копий

Тексты подсказок для интерфейса:

- **Полная** — каждый раз копируются все файлы. Надёжно и просто, но долго и занимает больше места.
- **Инкрементальная** — копируются только файлы, изменившиеся с прошлой копии любого типа. Быстро и экономно, но для восстановления нужна полная копия и все инкрементальные после неё.
- **Дифференциальная** — копируются файлы, изменившиеся с последней полной копии. С каждым разом копия растёт, зато для восстановления нужны только полная и последняя дифференциальная.
- **Зеркало** — в назначении поддерживается точная копия источника.
  - *Точное зеркало*: файлы, удалённые в источнике, удаляются и в копии.
  - *Безопасное зеркало*: удалённые и заменённые файлы переносятся в папку `_custos_deleted\ГГГГ-ММ-ДД ЧЧ-ММ\` с сохранением структуры и хранятся `safe_mirror_days` дней.

**Принудительная полная копия** для инкрементальных и дифференциальных заданий: каждые N запусков и/или в выбранный день недели или месяца.

### 6.2. Источники и фильтры

- Источники: папки, отдельные файлы, сетевые папки (UNC) со своей учётной записью. Флаг «включая подпапки».
- Маски включения и исключения (`*.tmp`, `~$*`), исключение папок по имени.
- Галочки «пропускать системные», «пропускать скрытые», «пропускать временные файлы».
- **Переменные в путях.** Системные переменные окружения и токены даты (`{yyyy}`, `{MM}`, `{dd}`, `{HH}`, `{mm}`, `{computer}`, `{task}`, `{type}`). Пользовательские переменные (`%USERPROFILE%`, `%APPDATA%`, `%LOCALAPPDATA%` и другие) раскрываются для профиля, указанного в `profile_sid` (по умолчанию для того, кто создал задание). Путь профиля берётся из `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList`. Это важно: служба работает от SYSTEM, и без этого `%USERPROFILE%` указывал бы на профиль системы.
- Дампы баз данных (MS SQL, PostgreSQL, 1С) делаются **скриптами в событиях «до»** (6.9). Встроенной поддержки СУБД нет.

### 6.3. Назначения

- Типы: локальная папка, сетевая папка (UNC), USB-диск, FTP и FTPS, SFTP, S3-совместимое хранилище, WebDAV (включая Nextcloud).
- **Несколько назначений у одного задания.** Данные читаются и сжимаются один раз и пишутся во все назначения одновременно. Сбой одного назначения не останавливает остальные, результат фиксируется по каждому назначению отдельно.
- **USB-диск** ищется по метке тома, поэтому смена буквы не мешает. Если диска нет, задание завершается ошибкой «Диск с меткой … не найден».
- **Учётная запись на каждое сетевое назначение** вместо «Run as» из Cobian. Доступ к шарам реализуется через `LogonUser(LOGON32_LOGON_NEW_CREDENTIALS)` и `WindowsIdentity.RunImpersonated`: локальные файлы читаются от SYSTEM, а в сеть программа ходит под указанной учёткой. Каждая учётка получает свою сессию входа, поэтому разные учётки к одному серверу (например, к `\\fileserver` под учётками `backup1`, `backup2` и `backup3`) не дают ошибку 1219.
- **Отключать сетевую папку сразу после копирования** (по умолчанию включено): закрыть все дескрипторы и освободить контекст входа, чтобы шара не оставалась подключённой.
- **Проверка свободного места** перед стартом. Оценка: объём к копированию, умноженный на коэффициент сжатия прошлого запуска. Если места не хватает, задание завершается ошибкой, ничего не записав. Для FTP, WebDAV и S3 проверка пропускается, если сервер не сообщает свободное место.
- **Ограничение скорости записи в сеть** в КБ/с, по умолчанию без ограничения.
- **Атомарность.** Файл пишется под именем `*.partial`, а после успешного завершения переименовывается. Для S3 то же даёт multipart upload. Незавершённая копия никогда не выглядит готовой.

### 6.4. Размещение и имена

- **«Отдельная папка для каждой копии»** (аналог «Create separated backups» в Cobian). Если включено, каждая копия без сжатия ложится в свою папку с датой и временем. Если выключено, используется одна общая папка, которая обновляется. Архивы всегда получают дату и время в имени.
- Шаблон имени: по умолчанию `{task} {yyyy}-{MM}-{dd} {HH}-{mm} ({type})`, где `{type}` = Full, Incremental, Differential.
- «Сохранять папку верхнего уровня» (как «Always create top directory» в Cobian), по умолчанию включено.
- «Удалять пустые папки в копии», по умолчанию выключено.

### 6.5. Сжатие, шифрование, проверка

- Форматы: без сжатия, ZIP, 7z. Уровень сжатия от 0 до 9.
- **7z доступен, только если все назначения задания допускают перемотку**: локальная папка, UNC, USB, SFTP. Формат 7z при создании возвращается к началу файла и дописывает заголовок, а FTP, WebDAV и S3 так не умеют. Для них остаются «без сжатия» и ZIP, который пишется потоком. В интерфейсе вариант 7z для таких заданий недоступен и рядом есть пояснение почему.
- Разбиение на тома (только 7z): готовые размеры 700 МБ, 4 ГБ (лимит FAT32), 4,3 ГБ (DVD) и свой размер.
- Шифрование AES-256 паролем, для 7z дополнительно шифрование имён файлов. Пароль хранится как учётные данные типа `archive_password`.
- **Проверка новой копии каждый N-й запуск** (`verify.every_runs`: 0 = никогда, 1 = каждый раз). Архивы проверяются тестовой распаковкой с контролем CRC, копии без сжатия — сверкой SHA-256 с манифестом (раздел 7). Данные читаются из назначения потоком, без записи на диск.
- **Плановая проверка хранящихся копий** раз в N дней (`verify.stored_every_days`, 0 = выключено). Проверка выполняется после очередного успешного запуска, если срок подошёл, и охватывает все наборы задания в назначении. Если какой-то набор повреждён, запуск получает статус `error`, а сервер показывает проблему (A.5, A.8).
- **Приоритет.** Потоки сжатия и копирования работают с приоритетом BelowNormal и низким приоритетом ввода-вывода. Процессор используется полностью, пока он свободен, но программа уступает пользователю и другим программам. В настройках можно выбрать «Обычный» приоритет.

### 6.6. Хранение копий

Режимы (`retention.mode`):

- **По количеству** — хранить N последних полных копий вместе с их инкрементальными и дифференциальными. Набор удаляется только целиком.
- **По возрасту** — удалять наборы старше N дней. Полная копия удаляется, только когда все зависящие от неё копии тоже старше срока.
- **Дед-отец-сын (GFS)** — хранить N дневных, N недельных и N месячных копий. Из каждого дня, недели и месяца остаётся последняя успешная. Это заменяет пары заданий «каждый день» плюс «каждую неделю» по одному источнику.

Железные правила:

- последняя успешная полная копия не удаляется никогда;
- если текущий запуск завершился ошибкой, ничего не удаляется;
- состав наборов определяется **сканированием назначения** (6.11), а не только по локальной базе: программа видит и копии, сделанные до переустановки.

### 6.7. Расписание и очередь

- Типы: ежедневно (можно выбрать дни недели и задать несколько времён), еженедельно, ежемесячно (числа месяца, «последний день»), по таймеру (каждые N минут), вручную.
- **Догоняющий запуск** (по умолчанию включён). Если машина была выключена или спала в момент запуска, после включения задание выполняется один раз с `trigger = catch_up` и `scheduled_for` = пропущенный слот. Учитывается только последний пропущенный слот за последние 7 дней.
- **Запрет сна** во время выполнения (`SetThreadExecutionState`).
- **Очередь строго последовательная**, порядок по `priority`. Если задание уже стоит в очереди или выполняется, повторно оно не ставится. Ручные и удалённые запуски тоже идут через очередь.

### 6.8. Открытые файлы и надёжность

- **VSS** включается для каждого задания отдельно. На каждый том источников создаётся теневая копия и освобождается после выполнения.
- Если VSS не удался, поведение задаётся в задании: отменить задание или продолжить без VSS с предупреждением.
- **Сохранение прав NTFS, атрибутов и дат** при копировании без сжатия. На сетевых назначениях права переносятся по возможности: ошибка установки прав даёт предупреждение, а не ошибку.
- **Повтор при ошибке чтения файла**: по умолчанию 1 повтор через 2 секунды (настраивается от 0 до 5).
- **Длинные пути** длиннее 260 символов поддерживаются.

### 6.9. События до и после

- Типы: запустить программу или скрипт (`.exe`, `.bat`, `.cmd`, `.ps1`) с аргументами и тайм-аутом, проверяя код возврата; остановить службу Windows; запустить службу Windows (с ожиданием нужного состояния).
- «Прервать задание, если событие „до“ завершилось ошибкой». Ошибка события «после» даёт предупреждение.
- **После выполнения**: выключить, перезагрузить, перевести в сон или гибернацию. Если в очереди есть другие задания, действие ждёт, пока очередь опустеет. Во всех сеансах показывается окно с отсчётом 60 секунд и кнопкой отмены.
- Скрипты выполняются от SYSTEM. Поэтому менять события могут только те, кому разрешено менять задания (раздел 4).

### 6.10. Журналы и история

- **Детальность**: «итоги и ошибки» или «каждый файл». Значение по умолчанию задаётся в настройках, задание может его переопределить.
- **Журнал в реальном времени** в окне программы. Плюс файл на каждый запуск.
- **История запусков** в программе: время, длительность, тип, файлы, объём, результат, ошибки.
- **Срок хранения журналов**: 180 дней по умолчанию, настраивается.
- **Windows Event Log**, источник `CUSTOS`:

| ID | Уровень | Событие |
|---|---|---|
| 1000 / 1001 | Info | Служба запущена / остановлена |
| 1100 / 1101 | Warning / Info | Связь с сервером потеряна / восстановлена |
| 2000 | Info | Задание начато |
| 2001 | Info | Задание выполнено успешно |
| 2002 | Warning | Выполнено с предупреждениями |
| 2003 | Error | Задание завершилось ошибкой |
| 2004 | Warning | Задание прервано |
| 2005 | Info | Выполнен догоняющий запуск |
| 3000 | Warning | VSS не удался |
| 3001 | Error | Недостаточно места в назначении |
| 4000 / 4001 | Info / Error | Обновление установлено / отклонено (неверная подпись) |

### 6.11. Восстановление (первая версия)

- Простое окно: выбрать задание **или** указать папку назначения (например, на новой машине, где локальной базы нет) → выбрать дату из списка наборов → выбрать папку (исходное место или другая) → восстановить.
- **Восстановление на дату**: программа собирает состояние из полной копии и цепочки инкрементальных или дифференциальных, по манифестам наборов (раздел 7). Файлы, удалённые до этой даты, не восстанавливаются.
- Для существующих файлов: пропустить, перезаписать или перезаписать только более старые.
- Восстанавливать может только администратор (раздел 4).
- Архивы остаются обычными 7z и ZIP: их можно открыть 7-Zip и без CUSTOS. Это нужно указать в README.

## 7. Как программа отслеживает изменения

- **Своя база вместо archive-бита.** Archive-бит один на файл и общий для всех заданий. Из-за этого в Cobian задания по одному источнику ломают друг другу инкременты. Например, если по папке `D:\Data` есть ежедневное инкрементальное и еженедельное полное задание, они сбрасывают один и тот же бит.
- Для каждого задания в SQLite хранится состояние файлов на момент последней успешной копии: путь, размер, время изменения (`LastWriteTimeUtc`). Отдельно хранится базовое состояние последней полной копии (для дифференциальных).
- База обновляется одной транзакцией **только после успешного запуска**. После неудачного запуска следующий снова возьмёт все изменения с момента последней успешной копии.
- **Манифест набора** `custos-set.json` пишется в каждый набор: в архив (для 7z с шифрованием имён — тоже в зашифрованном виде) или в папку набора. Состав манифеста:
  - id и имя задания, тип, время;
  - для инкрементальных и дифференциальных — id родительской полной копии;
  - список **всех** файлов источника на этот момент (путь, размер, время) с пометкой, какие лежат в этом наборе. Для файлов этого набора указывается SHA-256: он считается при копировании, пока файл всё равно читается.

  По манифестам работают хранение (6.6), восстановление на дату (6.11) и инвентаризация (A.8), даже если локальная база потеряна.
- Зеркало использует прямое сравнение источника и назначения по размеру и времени и в базе не нуждается.

## 8. Связь с сервером мониторинга

Полная спецификация — в приложении A. Здесь только то, что касается клиента.

- **Подключение** задаётся в настройках: адрес сервера и общий ключ регистрации. Можно указать их в установщике (10.1) или позже. Без сервера программа работает полностью автономно.
- **Ключи.** При первом запуске служба создаёт ключ агента. После регистрации закрепляет ключ сервера и показывает отпечатки обоих ключей.
- **Очередь отчётов.** `runs/start` и `runs/finish` пишутся в SQLite и отправляются по порядку. При недоступности сервера они копятся (A.11). Полный журнал отправляется при `warning` и `error`, журнал успешного запуска — только по запросу (`log.fetch`).
- **Прогресс** отправляется каждые 10 секунд во время выполнения, чтобы на сайте было видно, что сейчас копируется.
- **Синхронизация заданий в обе стороны.** Правки на месте и правки с сайта равноправны, побеждает последняя (A.4). Перезаписанная версия уходит на сервер в историю.
- «Разрешить серверу менять задания» включено по умолчанию. Эту настройку и адрес сервера можно изменить только локально.
- **Автообновление** через `update.install` (A.10): скачать, проверить SHA-256 и подпись сервера, запустить `Custos.Updater.exe`. Пакет с неверной подписью отклоняется (Event Log 4001).

Файл `.lst`: блоки `{11// ... //11}`, внутри строки `ключ=значение`. Пример лежит у автора; в репозиторий его кладём в `tests/fixtures/` **без строк `Passphrase` и `Run as Password`**.

| Cobian | CUSTOS | Проверено на примере |
|---|---|---|
| `Name`, `Enabled`, `Priority` | `name`, `enabled`, `priority` | да |
| `Backup type` | 0 → full, 1 → incremental; 2 → differential (предположительно) | 0 и 1 |

## 10. Установщик и сборка

### 10.1. Установщик (Inno Setup)

- Проверяет .NET 10 Desktop Runtime x64. Если его нет, ставит из дистрибутива, **вложенного в setup.exe**: интернет на машине не нужен.
- Регистрирует службу (автозапуск, перезапуск при сбое), источник Event Log и автозапуск интерфейса для всех пользователей.
- Страница мастера «Сервер мониторинга»: адрес и ключ регистрации, необязательно.
- Обновление поверх установленной версии сохраняет настройки и данные.
- Удаление: останавливает и удаляет службу, затем спрашивает, удалять ли настройки, журналы и базу. Сами резервные копии не удаляются никогда.
- Параметры тихой установки отдельно не делаем; стандартные `/SILENT` и `/VERYSILENT` у Inno Setup есть и так.

### 10.2. Репозиторий и сборка

Один репозиторий для клиента и сервера:

```
custos/
  client/
    Custos.sln
    src/Custos.Core/  src/Custos.Service/  src/Custos.Gui/  src/Custos.Updater/
    tests/Custos.Core.Tests/  tests/fixtures/
    installer/custos.iss
    build.ps1
  server/            (см. CUSTOS-monitor.md)
  LICENSE            (GPL-3.0)
  README.md  README.ru.md  THIRD-PARTY-NOTICES.txt
```

- Сборка на Windows. Нужны .NET 10 SDK, Inno Setup 6 и 7-Zip x64.
- `build.ps1` делает всё сам: `dotnet publish -c Release -r win-x64 --self-contained false`, берёт `7z.dll` из `C:\Program Files\7-Zip\`, собирает установщик (`ISCC.exe`) и пакет обновления (zip с `manifest.json`, A.10).
- Скрипт заранее проверяет, что всё нужное установлено, и понятно сообщает, чего не хватает.
- Подпись exe готовится заранее: если задан сертификат (переменная окружения), `build.ps1` подписывает файлы. Без сертификата сборка идёт без подписи.

## 11. Безопасность (сводка)

- Пароли и ключи хранятся только через DPAPI (SYSTEM). В Cobian пароли в `.lst` обратимы, у нас так быть не должно.
- Папка `config` закрыта ACL. Права проверяет служба, а не интерфейс (раздел 4).
- Канал до сервера защищён подписями обеих сторон и защитой от повтора. Секреты с сервера приходят зашифрованными на ключ агента (A.2).
- Обновления принимаются только с подписью сервера.
- При экспорте заданий пароли по умолчанию не выгружаются. Можно включить их выгрузку, зашифровав паролем экспорта (PBKDF2 + AES-256-GCM).
- В журналы не пишутся пароли, ключи и содержимое учётных данных.

## Приложение A. Общий контракт клиента и сервера

> Этот раздел **одинаков** в `CUSTOS-client.md` и `CUSTOS-monitor.md`. Клиент и сервер разрабатываются в разных чатах, поэтому этот текст единственное, что их связывает. Если в одном чате контракт пришлось изменить, правку нужно перенести в оба файла и увеличить версию протокола.

Версия протокола: **1**.

### A.1. Общие правила

- Транспорт: HTTP или HTTPS, JSON в UTF-8, `Content-Type: application/json`.
- Базовый адрес: `{server_url}/api/v1/`. `server_url` задаётся в клиенте, например `http://custos.lan`. Сервер может стоять и в подпапке.
- Каждый запрос агента несёт заголовок `X-Custos-Protocol: 1`.
- Время везде в UTC, формат ISO 8601: `2026-10-12T21:00:00Z`. Агент дополнительно сообщает свой часовой пояс в формате IANA (`Europe/Moscow`). В .NET его даёт `TimeZoneInfo.TryConvertWindowsIdToIanaId`.
- Идентификаторы: UUID v4 в виде строк. Агент сам генерирует id заданий, назначений, источников, учётных данных и запусков. Сервер генерирует `agent_id` и id команд.
- Сжатые поля (журналы): gzip, затем base64, поле с суффиксом `_gz_b64`.
- Размер тела запроса не больше 8 МБ. Полный журнал обрезается до 5 МБ после сжатия.

### A.2. Ключи и подписи

HTTP внутри локальной сети допустим, потому что подлинность обеих сторон обеспечивают подписи, а не транспорт.

- **Ключ агента.** RSA-3072, создаётся при первом запуске службы. Закрытый ключ хранится в `C:\ProgramData\CUSTOS\` под защитой DPAPI от имени SYSTEM.
- **Ключ сервера.** RSA-3072, создаётся при установке сервера (`bin/install.php`). Закрытый ключ лежит вне веб-корня.
- **Подпись:** RSASSA-PKCS1-v1_5 + SHA-256, результат в base64. PHP: `openssl_sign(..., OPENSSL_ALGO_SHA256)`. .NET: `RSA.SignData(..., HashAlgorithmName.SHA256, RSASignaturePadding.Pkcs1)`.
- **Отпечаток ключа:** первые 16 hex-символов SHA-256 от DER открытого ключа, группами по 4: `3F2A-91C0-77DE-0B14`. Показывается в GUI агента и на сайте, чтобы администратор мог их сверить.

**Запрос агента** (всё, кроме регистрации) несёт заголовки:

```
X-Custos-Agent: <agent_id>
X-Custos-Time: <unix-время, секунды>
X-Custos-Nonce: <32 hex-символа, случайные>
X-Custos-Signature: <base64>
```

Подписывается строка `"{METHOD}\n{PATH}\n{TIME}\n{NONCE}\n{sha256hex(body)}"`, где `PATH` — путь запроса вместе со строкой запроса, как он пришёл на сервер (`/api/v1/agent/heartbeat`). Для пустого тела берётся SHA-256 от пустой строки.

Сервер проверяет подпись открытым ключом агента, расхождение времени (не больше 300 с) и уникальность nonce для этого агента в течение 10 минут. При ошибке отвечает 401.

**Ответ сервера** несёт заголовки `X-Custos-Time` и `X-Custos-Signature`. Подписывается строка `"{TIME}\n{NONCE из запроса}\n{sha256hex(body)}"`. Агент проверяет её закреплённым открытым ключом сервера. Ответ с неверной подписью агент отбрасывает так же, как недоступность сервера, и пишет об этом в журнал. Поэтому подменить команды в сети нельзя.

**Секреты, которые сервер передаёт агенту** (пароли шар, FTP, ключи S3 и SFTP, пароль архива), шифруются гибридно. Случайный ключ AES-256 шифруется RSA-OAEP (SHA-1, MGF1-SHA1) на открытом ключе агента, сами данные шифруются AES-256-GCM.

`secret_enc` = base64( зашифрованный ключ, 384 байта ‖ nonce, 12 байт ‖ шифртекст ‖ tag, 16 байт ).

- PHP: `openssl_public_encrypt(..., OPENSSL_PKCS1_OAEP_PADDING)` и `openssl_encrypt('aes-256-gcm', ..., OPENSSL_RAW_DATA, $nonce, $tag)`.
- .NET: `RSA.Decrypt(..., RSAEncryptionPadding.OaepSHA1)` и `AesGcm`.

Агент расшифровывает секрет и сразу сохраняет его через DPAPI. **Сервер не хранит секреты в открытом виде и никогда не получает их от агента.**

**Пароль программы** передаётся только как хэш: `pbkdf2-sha256$<итерации>$<salt base64>$<hash base64>`, 200 000 итераций, соль 16 байт, хэш 32 байта. Сервер вычисляет его через `hash_pbkdf2`, агент через `Rfc2898DeriveBytes.Pbkdf2`.

### A.3. Регистрация агента

1. Администратор задаёт на сервере общий ключ регистрации.
2. Агент отправляет `POST /api/v1/agent/register` без заголовков подписи:

```json
{
  "registration_key": "общий-ключ",
  "hostname": "PC-01",
  "machine_guid": "значение HKLM\\SOFTWARE\\Microsoft\\Cryptography\\MachineGuid",
  "os": "Windows 11 Pro 24H2 (26100)",
  "agent_version": "1.0.0",
  "time_zone": "Europe/Moscow",
  "public_key": "-----BEGIN PUBLIC KEY-----\n...",
  "proof": "base64 подписи строки \"{registration_key}\\n{hostname}\\n{machine_guid}\" ключом агента"
}
```

3. Ответ `200`:

```json
{ "agent_id": "uuid", "status": "pending", "server_public_key": "-----BEGIN PUBLIC KEY-----\n...", "server_name": "CUSTOS" }
```

   Неверный ключ: `403 bad_registration_key`. Агент закрепляет ключ сервера (TOFU) и показывает в GUI «Ожидает подтверждения на сервере» с отпечатками обоих ключей.
4. Администратор подтверждает агента на сайте. До подтверждения сервер принимает от агента только heartbeat. Отчёты о запусках копятся в очереди агента.
5. **Повторная установка.** Если с тем же `machine_guid` уже есть агент, новая регистрация попадает в ожидающие с пометкой «повторная регистрация». Администратор выбирает: заменить существующий (история и задания сохраняются, ключ меняется) или завести новый.
6. Если сервер отвечает `404 unknown_agent` (агента удалили), агент сбрасывает `agent_id` и регистрируется заново.

### A.4. Heartbeat и команды

`POST /api/v1/agent/heartbeat` отправляется каждые `heartbeat_interval_s` секунд (по умолчанию 60). Это быстрый «пульс», через него же приходят команды.

Запрос:

```json
{
  "agent_version": "1.0.0",
  "config_revision": 42,
  "time_zone": "Europe/Moscow",
  "service_started_at": "2026-10-12T05:01:10Z",
  "state": "idle",
  "running": null,
  "queue": ["task-uuid-2", "task-uuid-5"]
}
```

`state`: `idle` или `running`. Во время работы `running` = `{"run_id": "...", "task_id": "..."}`. `queue` — задания, стоящие в очереди.

Ответ:

```json
{
  "status": "approved",
  "server_time": "2026-10-12T13:00:00Z",
  "heartbeat_interval_s": 60,
  "want_config": false,
  "commands": [
    { "id": "cmd-uuid", "kind": "task.run", "payload": { "task_id": "..." }, "expires_at": "2026-10-12T14:00:00Z" }
  ]
}
```

- `status`: `pending`, `approved` или `disabled`. Отключённый (`disabled`) агент продолжает работать автономно и шлёт только heartbeat раз в 10 минут.
- `want_config: true` значит, что сервер просит полный снимок конфигурации (A.6). Так бывает после подтверждения или при расхождении `config_revision`.
- Команду с истёкшим `expires_at` агент отклоняет.

Результат команды: `POST /api/v1/agent/commands/{id}/result` с телом `{"status": "done|failed|rejected", "message": "..."}`.

| `kind` | `payload` | Что делает агент |
|---|---|---|
| `task.run` | `{task_id}` | Ставит задание в очередь с `trigger: "remote"` |
| `task.stop` | `{task_id}` | Прерывает выполнение (статус `aborted`) |
| `task.pause` / `task.resume` | `{task_id}` | Пауза и продолжение |
| `task.enable` / `task.disable` | `{task_id}` | Включает или отключает задание |
| `task.upsert` | `{task, base_revision, secrets}` | Создаёт или изменяет задание (см. ниже) |
| `task.delete` | `{task_id}` | Удаляет задание (сами копии в хранилище не трогает) |
| `settings.update` | `{settings}` (частично) | Меняет настройки из A.9, кроме локальных |
| `log.fetch` | `{run_id}` | Выгружает полный журнал запуска (A.7) |
| `inventory.refresh` | `{}` | Отправляет инвентаризацию (A.8) |
| `update.install` | `{version, sha256, signature}` | Скачивает и ставит обновление (A.10) |

Если на агенте выключено «Разрешить серверу менять задания», команды `task.upsert`, `task.delete`, `task.enable`, `task.disable` и `settings.update` отклоняются (`rejected`).

**`task.upsert` и конфликты.** `secrets` — объект `{ "<credential_id>": { "kind", "user", "domain", "secret_enc" } }`, где `secret_enc` зашифрован по A.2. Правило конфликтов: **побеждает последняя правка**. Агент применяет изменение, даже если `base_revision` не совпадает с текущей ревизией задания. В этом случае он отвечает `done` с `message: "conflict: local revision N overwritten"` и прикладывает перезаписанную версию к ближайшему снимку конфигурации в поле `overwritten`. Новая ревизия задания = max(локальная, `base_revision`) + 1, `updated_by` = `server:<логин>`.

### A.5. Запуски

`POST /api/v1/agent/runs/start`:

```json
{
  "run_id": "uuid", "task_id": "uuid", "task_revision": 7,
  "backup_type": "incremental",
  "trigger": "schedule",
  "scheduled_for": "2026-10-12T21:00:00Z",
  "started_at": "2026-10-12T21:00:02Z"
}
```

- `trigger`: `schedule`, `catch_up` (догоняющий запуск после выключения), `manual` (кнопка в GUI) или `remote` (команда с сервера).
- `scheduled_for` — слот расписания, к которому относится запуск. Для `schedule` и `catch_up` он обязателен, для `manual` и `remote` равен `null`. По нему сервер сопоставляет запуски с ожидаемым расписанием.

`POST /api/v1/agent/runs/progress` отправляется каждые 10 секунд во время выполнения. В очередь не ставится.

```json
{
  "run_id": "uuid", "phase": "copy", "percent": 37.5,
  "files_done": 1200, "files_total": 3200, "bytes_done": 104857600, "bytes_total": 279620266,
  "speed_bps": 52428800, "eta_s": 210, "current_file": "D:\\Data\\reports\\2026-10.pdf"
}
```

`phase`: `pre_events`, `vss`, `scan`, `copy`, `verify`, `retention`, `post_events`.

`POST /api/v1/agent/runs/finish`:

```json
{
  "run_id": "uuid", "task_id": "uuid", "status": "warning",
  "finished_at": "2026-10-12T21:04:40Z",
  "source_files": 3200, "source_bytes": 279620266,
  "files_processed": 3197, "bytes_written": 98112000,
  "errors": 0, "warnings": 3,
  "error_message": null,
  "destinations": [
    { "destination_id": "uuid", "status": "success", "set_name": "Documents 2026-10-12 21-00 (Incremental)", "bytes": 98112000, "error": null }
  ],
  "verify": { "performed": true, "ok": true, "scope": "new", "sets_checked": 1, "failed_sets": [] },
  "retention": { "deleted_sets": 1 },
  "log_tail": "последние 100 строк журнала",
  "log_gz_b64": "есть только при status warning или error"
}
```

- `status`: `success`, `warning` (выполнено, но часть файлов пропущена), `error` или `aborted` (остановлено пользователем или командой).
- `source_files` и `source_bytes` описывают весь источник на момент запуска, даже при инкрементальной копии: по ним сервер ищет аномалии.
- `verify.scope`: `new` (проверена только что созданная копия) или `stored` (плановая проверка всех хранящихся наборов). Если какой-то набор не прошёл проверку, его имя попадает в `failed_sets`, а статус запуска становится `error` с `error_message` вида «Повреждён набор …».
- `start` и `finish` идемпотентны по `run_id`. При недоступности сервера они сохраняются в локальной очереди агента и отправляются позже строго по порядку.

### A.6. Снимок конфигурации

`POST /api/v1/agent/config` отправляется через 10 секунд после последнего локального изменения и по запросу `want_config`.

```json
{
  "config_revision": 43,
  "changed": [ { "task_id": "uuid", "revision": 8, "updated_by": "local:OFFICE\\user1", "updated_at": "..." } ],
  "settings": { "...": "объект A.9" },
  "credentials": [ { "id": "uuid", "kind": "windows", "user": "backup1", "domain": ".", "has_secret": true } ],
  "tasks": [ "объекты A.9 без секретов" ],
  "deleted_task_ids": [],
  "overwritten": [ "перезаписанные версии заданий (A.4), если были" ]
}
```

`updated_by` имеет вид `local:<ДОМЕН\пользователь>` для правок в программе или `server:<логин>` для правок с сайта. Правки `local:` сайт показывает ненавязчивым уведомлением.

### A.7. Журнал по запросу

`POST /api/v1/agent/runs/{run_id}/log` с телом `{"log_gz_b64": "..."}`. Это ответ на команду `log.fetch`. Если журнал уже удалён по сроку хранения, команда завершается `failed`.

### A.8. Инвентаризация хранилищ

`POST /api/v1/agent/inventory` отправляется после каждого запуска, раз в 6 часов и по команде.

```json
{
  "destinations": [
    {
      "task_id": "uuid", "destination_id": "uuid", "kind": "unc", "path": "\\\\fileserver\\docs",
      "total_bytes": 4000000000000, "free_bytes": 1250000000000,
      "sets": [ { "name": "Documents 2026-10-12 00-30 (Full)", "type": "full", "time": "2026-10-11T21:30:00Z", "bytes": 5100000000, "verified_at": "2026-10-12T21:10:00Z", "verify_ok": true } ]

```

Для FTP, WebDAV и S3 поля `total_bytes` и `free_bytes` могут быть `null`. Если набор ещё не проверялся, `verified_at` и `verify_ok` равны `null`.

### A.9. Объекты: задание, учётные данные, настройки

**Задание** (`task`). Значения по умолчанию указаны в комментариях. Неизвестные поля обе стороны сохраняют и не удаляют: это защита от расхождения версий.

```jsonc
{
  "id": "uuid",
  "revision": 7,
  "updated_at": "2026-10-12T10:00:00Z",
  "updated_by": "local:OFFICE\\admin",
  "name": "Documents",
  "enabled": true,
  "comment": "",
  "priority": 0,                       // больше = раньше в очереди

  "mirror_mode": null,                 // exact | safe, только для mirror
  "force_full": { "every_runs": 0, "weekday": null, "month_day": null },  // weekday 1–7 (ISO, 1 = пн), month_day 1–31 или -1 = последний день

      "id": "uuid", "kind": "unc",     // local | unc | usb | ftp | ftps | sftp | s3 | webdav
      "path": "\\\\fileserver\\docs",
```

`kind`: `windows` (шары), `ftp`, `sftp` (пароль или закрытый ключ), `s3` (`user` = access key, секрет = secret key), `webdav`, `archive_password`. Секрет хранится только на агенте под DPAPI и никогда не уходит на сервер.

### A.10. Обновления агента

Команда `update.install` несёт `version`, `sha256` пакета и `signature`: подпись сервера (A.2) строки `"{version}\n{sha256}"`. Агент скачивает пакет `GET /api/v1/agent/updates/{version}` (запрос подписан как обычно), проверяет SHA-256 и подпись, затем устанавливает. Новую версию сервер видит по следующему heartbeat. Пакет — zip с файлами программы и `manifest.json` (`version`, `min_protocol`, список файлов).

### A.11. Ошибки

Тело ошибки: `{"error": "код", "message": "текст"}`.

| HTTP | `error` | Действие агента |
|---|---|---|
| 400 | `bad_request` | Записать в журнал, не повторять |
| 401 | `bad_signature`, `clock_skew` | При `clock_skew` в теле есть `server_time`: записать «расходится время» |
| 403 | `pending`, `disabled`, `bad_registration_key` | Ждать, отчёты держать в очереди |
| 404 | `unknown_agent` | Зарегистрироваться заново (A.3) |
| 413 | `too_large` | Отправить без `log_gz_b64` |
| 429 | `rate_limited` | Ждать столько, сколько указано в `Retry-After` |
| 5xx / нет связи | — | Повторять через 1, 2, 5, 10, 10… минут |

### A.12. Статусы (общий словарь)

| Код | Где | Русское название | Смысл |
|---|---|---|---|
| `success` | запуск | Успешно | Всё скопировано |
| `warning` | запуск | С предупреждениями | Выполнено, часть файлов пропущена |
| `error` | запуск | Ошибка | Копия не создана или создана не полностью |
| `aborted` | запуск | Прервано | Остановлено вручную или командой |
| `running` | задание | Выполняется | Есть активный запуск |
| `missed` | задание | Пропущено | Слот расписания прошёл, машина была на связи, а запуска не было. **Это проблема** |
| `missed_offline` | задание | Пропущено, машина выключена | Слот прошёл, когда машина была не на связи. Не проблема, ждём догоняющий запуск |
| `stale` | задание | Давно нет успешной копии | Последняя успешная копия старше N дней (по умолчанию 7). Мягкая пометка |
| `online` / `offline` | агент | На связи / Не на связи | `offline`: нет heartbeat дольше N минут (по умолчанию 60). Само по себе не проблема |
| `pending` | агент | Ожидает подтверждения | Зарегистрирован, но не подтверждён |
| `disabled` | агент или задание | Отключено | — |
