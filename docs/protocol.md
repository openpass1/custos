# CUSTOS — общий контракт клиента и сервера

Приложение A к обоим техническим заданиям проекта: [`CUSTOS-client.md`](CUSTOS-client.md) (программа для Windows) и [`CUSTOS-monitor.md`](CUSTOS-monitor.md) (сервер мониторинга). Ссылки вида «A.9» в обоих ТЗ ведут сюда.

> Клиент и сервер разрабатываются отдельно, поэтому этот файл единственное, что их связывает. Контракт существует **в одном экземпляре**: любая правка вносится только сюда и записывается в журнал изменений (A.13). Там же сказано, когда меняется версия протокола.

Версия протокола: **1**. Редакция документа от 29.10.2026.

### A.1. Общие правила

- Транспорт: HTTP или HTTPS, JSON в UTF-8, `Content-Type: application/json`.
- Базовый адрес: `{server_url}/api/v1/`. `server_url` задаётся в клиенте без косой черты в конце, например `http://custos.lan`. Сервер может стоять и в подпапке, и за обратным прокси (условие для прокси — в A.2).
- Каждый запрос агента несёт заголовок `X-Custos-Protocol: 1`.
- Время везде в UTC, формат ISO 8601: `2026-10-12T21:00:00Z`. Агент дополнительно сообщает свой часовой пояс в формате IANA (`Europe/Moscow`). В .NET его даёт `TimeZoneInfo.TryConvertWindowsIdToIanaId`.
- Идентификаторы: UUID v4 в виде строк. Агент сам генерирует id заданий, назначений, источников, учётных данных и запусков. Сервер генерирует `agent_id` и id команд.
- Сжатые поля (журналы): gzip, затем base64, поле с суффиксом `_gz_b64`.
- Размер тела запроса не больше 8 МБ. Полный журнал обрезается до 5 МБ после сжатия.

### A.2. Ключи и подписи

HTTP внутри локальной сети допустим, потому что подлинность обеих сторон обеспечивают подписи, а не транспорт.

- **Ключ агента.** RSA-3072, создаётся при первом запуске службы. Закрытый ключ хранится в `C:\ProgramData\CUSTOS\` под защитой DPAPI от имени SYSTEM.
- **Ключ сервера.** RSA-3072, создаётся при установке сервера (`bin/install.php`). Закрытый ключ лежит вне веб-корня.
- **Подпись:** RSASSA-PKCS1-v1_5 + SHA-256, результат в base64. PHP: `openssl_sign(..., OPENSSL_ALGO_SHA256)`. .NET: `RSA.SignData(..., HashAlgorithmName.SHA256, RSASignaturePadding.Pkcs1)`.
- **Отпечаток ключа:** первые 16 hex-символов SHA-256 от DER открытого ключа, группами по 4: `3F2A-91C0-77DE-0B14`. Показывается в GUI агента и на сайте, чтобы администратор мог их сверить.
- **HMAC:** HMAC-SHA256, результат в base64. Нужен только при регистрации (A.3). PHP: `hash_hmac('sha256', ..., true)`, сравнение через `hash_equals`. .NET: `HMACSHA256.HashData`, сравнение через `CryptographicOperations.FixedTimeEquals`.

**Запрос агента** несёт заголовки:

```
X-Custos-Agent: <agent_id>
X-Custos-Time: <unix-время, секунды>
X-Custos-Nonce: <32 hex-символа, случайные>
X-Custos-Signature: <base64>
```

Подписывается строка `"{METHOD}\n{PATH}\n{TIME}\n{NONCE}\n{sha256hex(body)}"`. Для пустого тела берётся SHA-256 от пустой строки. Регистрация подписывается так же, только без `X-Custos-Agent` и с дополнительным заголовком (A.3).

`PATH` — путь запроса **относительно базового адреса API** вместе со строкой запроса, без косой черты в начале: `agent/heartbeat`, `agent/commands/<id>/result`, `agent/updates/1.1.0`. Сервер получает его из `REQUEST_URI`: берёт всё, что идёт после первого вхождения `/api/v1/`. Поэтому подпись не зависит от того, стоит ли сервер в подпапке (`http://host/custos/api/v1/…`) и меняет ли обратный прокси начало пути. Условие для прокси одно: часть пути начиная с `/api/v1/` он передаёт без изменений. Агент собирает пути только из латинских букв, цифр и символов `- . _ /`, поэтому кодирование URL на подпись не влияет.

Сервер проверяет подпись открытым ключом агента, расхождение времени (не больше 300 с) и уникальность nonce для этого агента в течение 10 минут. При ошибке отвечает 401.

**Ответ сервера.** Подписан **каждый** ответ на запрос к `api/v1/agent/…`: и успешный, и с ошибкой (400, 401, 403, 404, 413, 429, а также 5xx, если его формирует сам PHP), включая ответы на регистрацию. Ответ несёт заголовки:

```
X-Custos-Time: <unix-время сервера, секунды>
X-Custos-Signature: <base64>
```

Подписывается строка `"{STATUS}\n{TIME}\n{NONCE}\n{sha256hex(body)}"`:

- `STATUS` — трёхзначный код HTTP (`200`, `404`). Он входит в подпись, чтобы подписанный ответ нельзя было выдать за ответ с другим кодом;
- `NONCE` — значение `X-Custos-Nonce` из запроса;
- `body` — тело ответа после снятия `Content-Encoding`: если nginx сжимает ответы gzip, хэш считается от распакованного тела.

Агент проверяет подпись закреплённым открытым ключом сервера. Свежесть ответа обеспечивает nonce из запроса, поэтому время `X-Custos-Time` со своими часами агент не сравнивает. Ответ без подписи или с неверной подписью агент отбрасывает так же, как недоступность сервера, **какой бы код HTTP в нём ни был**, и пишет об этом в журнал. Единственное исключение — неподписанный 413 (A.11). Неподписанные ответы — это прежде всего ошибки самого nginx (502, 504) и промежуточных устройств, для агента они ничем не отличаются от недоступности сервера.

Поэтому в сети нельзя подменить ни команды, ни ошибки: поддельный `404 unknown_agent` не заставит агента зарегистрироваться заново, а поддельный `403` не остановит отправку отчётов.

**Пакет обновления** (`GET agent/updates/{version}`) и **установщик 7-Zip** (`GET agent/sevenzip/{version}`), A.10, — единственные ответы, тело которых подписью ответа не покрывается: у успешного ответа с двоичным файлом заголовков `X-Custos-Time` и `X-Custos-Signature` может не быть. Целостность файла обеспечивают SHA-256 и подпись сервера из команды `update.install` или `sevenzip.update`, а сама команда пришла в подписанном ответе heartbeat. Ошибки этих запросов (JSON, например `400 bad_request`, если такого файла на сервере нет) подписываются как обычно.

**Секреты, которые сервер передаёт агенту** (пароли шар, FTP, ключи S3 и SFTP, пароль архива), шифруются гибридно. Случайный ключ AES-256 шифруется RSA-OAEP (SHA-1, MGF1-SHA1) на открытом ключе агента, сами данные шифруются AES-256-GCM.

`secret_enc` = base64( зашифрованный ключ, 384 байта ‖ nonce, 12 байт ‖ шифртекст ‖ tag, 16 байт ).

- PHP: `openssl_public_encrypt(..., OPENSSL_PKCS1_OAEP_PADDING)` и `openssl_encrypt('aes-256-gcm', ..., OPENSSL_RAW_DATA, $nonce, $tag)`.
- .NET: `RSA.Decrypt(..., RSAEncryptionPadding.OaepSHA1)` и `AesGcm`.

Агент расшифровывает секрет и сразу сохраняет его через DPAPI. **Сервер не хранит секреты в открытом виде и никогда не получает их от агента.**

**Пароль программы** передаётся только как хэш: `pbkdf2-sha256$<итерации>$<salt base64>$<hash base64>`, 200 000 итераций, соль 16 байт, хэш 32 байта. Сервер вычисляет его через `hash_pbkdf2`, агент через `Rfc2898DeriveBytes.Pbkdf2`.

### A.3. Регистрация агента

**Ключ регистрации** общий для всех агентов. Его генерирует сам сервер: 25 случайных символов из алфавита Base32 (`A–Z`, `2–7`), около 125 бит. Показывается группами по 5 через дефис: `K7QHM-2XARV-4NTB6-EWZ3P-LC5DQ`. Задать свой ключ нельзя: короткий ключ можно подобрать перебором по одной перехваченной регистрации. Новый ключ можно сгенерировать в любой момент, уже зарегистрированным агентам это не мешает.

**Код регистрации** — ключ и, по желанию, через `#` отпечаток ключа сервера:

```
K7QHM-2XARV-4NTB6-EWZ3P-LC5DQ#3F2A-91C0-77DE-0B14
```

**Строка подключения** — то, что администратор вставляет в установщике или в настройках программы: адрес сайта и код регистрации одной строкой, через `#`. Агенту всегда нужно и то и другое, поэтому сайт показывает только эту строку, её можно просто скопировать:

```
http://custos.lan#K7QHM-2XARV-4NTB6-EWZ3P-LC5DQ#3F2A-91C0-77DE-0B14
```

Адрес — всё до первого `#`, остальное — код регистрации.

Отпечаток в коде необязателен: строка `http://custos.lan#K7QHM-2XARV-4NTB6-EWZ3P-LC5DQ` тоже подходит. Перед использованием агент убирает из ключа пробелы и дефисы и переводит его в верхний регистр: `K7QHM2XARV4NTB6EWZ3PLC5DQ`. Ключом HMAC служат байты этой строки в ASCII. Код регистрации хранится на агенте под DPAPI, в снимок конфигурации (A.6) не попадает и на сервер не отправляется.

**Ключ регистрации никогда не передаётся по сети.** Агент доказывает, что знает его, через HMAC запроса, а по HMAC ответа проверяет, что ответил сервер, который этот ключ тоже знает. Без ключа нельзя ни зарегистрировать агента, ни подменить ответ сервера при первом подключении.

1. Агент отправляет `POST /api/v1/agent/register`. Заголовки как в A.2, только без `X-Custos-Agent` и с HMAC:

```
X-Custos-Time: <unix-время, секунды>
X-Custos-Nonce: <32 hex-символа, случайные>
X-Custos-Signature: <подпись строки запроса ключом агента, A.2>
X-Custos-Registration-Mac: <HMAC той же строки на ключе регистрации>
```

   Тело:

```json
{
  "hostname": "PC-01",
  "machine_guid": "значение HKLM\\SOFTWARE\\Microsoft\\Cryptography\\MachineGuid",
  "os": "Windows 11 Pro 24H2 (26100)",
  "agent_version": "1.0.0",
  "time_zone": "Europe/Moscow",
  "public_key": "-----BEGIN PUBLIC KEY-----\n..."
}
```

   `X-Custos-Signature` проверяется ключом `public_key` из тела и доказывает, что у агента есть закрытый ключ.

2. Сервер проверяет расхождение времени и nonce, как в A.2 (nonce регистраций проверяются на уникальность среди всех регистраций), затем HMAC на текущем ключе регистрации (не совпал → `403 bad_registration_key`), затем подпись (`401 bad_signature`).

3. Ответ `200`:

```json
{ "agent_id": "uuid", "status": "pending", "server_public_key": "-----BEGIN PUBLIC KEY-----\n...", "server_name": "CUSTOS" }
```

   Кроме обычной подписи (A.2) ответ несёт заголовок `X-Custos-Registration-Mac`: HMAC строки ответа `"{STATUS}\n{TIME}\n{NONCE}\n{sha256hex(body)}"` на ключе регистрации. Ответы с ошибками регистрации подписываются так же, обоими способами. Исключение — `403 bad_registration_key`: сервер не знает, каким ключом агент считал HMAC, поэтому этот ответ подписан только ключом сервера.

   Агент принимает ответ, только если выполнены все условия:
   - `X-Custos-Registration-Mac` верен: ответ построил тот, кто знает ключ регистрации, и именно на этот запрос (в строке ответа стоит nonce агента);
   - `X-Custos-Signature` верна для `server_public_key` из тела: у отвечающего есть закрытый ключ сервера;
   - если в коде регистрации есть отпечаток, он совпадает с отпечатком `server_public_key`;
   - при повторной регистрации (п. 6) `server_public_key` совпадает с уже закреплённым ключом.

   Иначе регистрация не засчитывается: агент ничего у себя не меняет, пишет причину в журнал, показывает её в GUI и повторяет попытку через 10 минут. Ответ `403 bad_registration_key` агент проверить не может (ключ у него другой) и показывает как «ключ регистрации не подошёл».

   Приняв ответ, агент закрепляет ключ сервера и показывает в GUI «Ожидает подтверждения на сервере» с отпечатками обоих ключей. Если отпечатка в коде регистрации не было, ключ сервера закрепляется по первому проверенному ответу (TOFU), а его отпечаток можно сверить вручную с настройками сайта.
4. Администратор подтверждает агента на сайте, сверив отпечаток ключа агента с окном программы на машине. До подтверждения сервер принимает от агента только heartbeat. Отчёты о запусках копятся в очереди агента.
5. **Повторная установка.** Если с тем же `machine_guid` уже есть агент, новая регистрация попадает в ожидающие с пометкой «повторная регистрация». Администратор выбирает: заменить существующий (история и задания сохраняются, ключ меняется) или завести новый.
6. Если сервер отвечает `404 unknown_agent` (агента удалили), агент сбрасывает `agent_id` и регистрируется заново с сохранённым кодом регистрации. Этот ответ подписан закреплённым ключом сервера, поэтому подделать его нельзя. При повторной регистрации агент принимает только уже закреплённый ключ сервера.
7. **Смена ключа сервера.** Ответы, подписанные не закреплённым ключом, агент считает неподписанными, то есть сервер для него недоступен. Если сервер переустановили с новыми ключами или машину переводят на другой сервер, администратор машины нажимает в настройках программы «Сбросить привязку к серверу» и при необходимости вводит новый код регистрации. Агент забывает `agent_id` и ключ сервера и регистрируется заново. С сервера это сделать нельзя.
8. **Уже известный ключ агента.** Сервер узнаёт агента по его ключу. Регистрация, подписанная ключом, который уже есть на сервере, возвращает того же агента (`agent_id`) с его прежним статусом, и подтверждать его заново не нужно. Так бывает, когда после «Сбросить привязку к серверу» машину подключают к тому же серверу: ключ агента при сбросе не меняется. Это безопасно: подписать такой запрос может только владелец закрытого ключа, который администратор уже подтвердил. Удалённый на сайте агент (п. 6) сервер больше не знает, поэтому он появляется заново в ожидающих.

### A.4. Heartbeat и команды

`POST /api/v1/agent/heartbeat` отправляется каждые `heartbeat_interval_s` секунд (по умолчанию 20). Это быстрый «пульс», через него же приходят команды.

Запрос:

```json
{
  "agent_version": "1.0.0",
  "sevenzip_version": "24.09",
  "config_revision": 42,
  "time_zone": "Europe/Moscow",
  "service_started_at": "2026-10-12T05:01:10Z",
  "state": "idle",
  "running": null,
  "queue": ["task-uuid-2", "task-uuid-5"]
}
```

`sevenzip_version` — версия `7z.dll`, которую загрузила служба, в виде `"24.09"` (как называются выпуски 7-Zip: из версии файла 24.9.0.0 получается `24.09`). Поле необязательное: `null` или его отсутствие значит, что `7z.dll` не загружен или агент не сообщает версию. По нему сервер показывает версию 7-Zip на машинах и предлагает обновление (A.10).

`state`: `idle`, `running` или `paused`. Во время работы `running` = `{"run_id": "...", "task_id": "...", "paused_at": null}`. `queue` — задания, стоящие в очереди.

`paused` значит, что текущий запуск поставлен на паузу кнопкой в программе или командой `task.pause`. Объект `running` при этом остаётся тем же, а в `paused_at` стоит время постановки на паузу. Пока запуск на паузе, очередь стоит: следующее задание начнётся только после продолжения или прерывания этого запуска.

Ответ:

```json
{
  "status": "approved",
  "server_time": "2026-10-12T13:00:00Z",
  "heartbeat_interval_s": 20,
  "want_config": false,
  "commands": [
    { "id": "cmd-uuid", "kind": "task.run", "payload": { "task_id": "..." }, "expires_at": "2026-10-12T14:00:00Z" }
  ]
}
```

- `status`: `pending`, `approved` или `disabled`. Отключённый (`disabled`) агент продолжает работать автономно и шлёт только heartbeat, с интервалом `heartbeat_interval_s` из ответа. Отключённому агенту сервер даёт 300 секунд, поэтому после включения на сайте машина возвращается не позже чем через 5 минут.
- `want_config: true` значит, что сервер просит полный снимок конфигурации (A.6). Так бывает после подтверждения или при расхождении `config_revision`.
- Команду с истёкшим `expires_at` агент отклоняет.

Результат команды: `POST /api/v1/agent/commands/{id}/result` с телом `{"status": "done|failed|rejected", "message": "..."}`.

| `kind` | `payload` | Что делает агент |
|---|---|---|
| `task.run` | `{task_id}` | Ставит задание в очередь с `trigger: "remote"` |
| `task.stop` | `{task_id}` | Прерывает выполнение (статус `aborted`) |
| `task.pause` / `task.resume` | `{task_id}` | Пауза и продолжение |
| `task.enable` / `task.disable` | `{task_id}` | Включает или отключает задание |
| `task.upsert` | `{task, base_revision, secrets}` | Создаёт или изменяет задание (см. ниже) |
| `task.delete` | `{task_id}` | Удаляет задание (сами копии в хранилище не трогает) |
| `settings.update` | `{settings}` (частично) | Меняет настройки из A.9, кроме локальных |
| `log.fetch` | `{run_id}` | Выгружает полный журнал запуска (A.7) |
| `inventory.refresh` | `{}` | Отправляет инвентаризацию (A.8) |
| `update.install` | `{version, sha256, signature}` | Скачивает и ставит обновление (A.10) |
| `sevenzip.update` | `{version, sha256, signature}` | Скачивает установщик 7-Zip, достаёт из него `7z.dll` и заменяет им свой (A.10) |

Если на агенте выключено «Разрешить серверу менять задания», команды `task.upsert`, `task.delete`, `task.enable`, `task.disable` и `settings.update` отклоняются (`rejected`).

**`task.upsert` и конфликты.** `secrets` — объект `{ "<credential_id>": { "kind", "user", "domain", "secret_enc" } }`, где `secret_enc` зашифрован по A.2. Агент создаёт учётную запись с этим `id` или, если она уже есть, заменяет её имя и секрет. Так с сайта приходят и новые учётные записи, и новые пароли старых; задание ссылается на них по `credential_id` как обычно. Правило конфликтов: **побеждает последняя правка**. Агент применяет изменение, даже если `base_revision` не совпадает с текущей ревизией задания. В этом случае он отвечает `done` с `message: "conflict: local revision N overwritten"` и прикладывает перезаписанную версию к ближайшему снимку конфигурации в поле `overwritten`. Новая ревизия задания = max(локальная, `base_revision`) + 1, `updated_by` = `server:<логин>`.

### A.5. Запуски

`POST /api/v1/agent/runs/start`:

```json
{
  "run_id": "uuid", "task_id": "uuid", "task_revision": 7,
  "backup_type": "incremental",
  "trigger": "schedule",
  "scheduled_for": "2026-10-12T21:00:00Z",
  "started_at": "2026-10-12T21:00:02Z"
}
```

- `trigger`: `schedule`, `catch_up` (догоняющий запуск после выключения), `manual` (кнопка в GUI) или `remote` (команда с сервера).
- `scheduled_for` — слот расписания, к которому относится запуск. Для `schedule` и `catch_up` он обязателен, для `manual` и `remote` равен `null`. По нему сервер сопоставляет запуски с ожидаемым расписанием.

`POST /api/v1/agent/runs/progress` отправляется каждые 10 секунд во время выполнения. На паузе не отправляется: паузу сервер видит по heartbeat (A.4). В очередь не ставится.

```json
{
  "run_id": "uuid", "phase": "copy", "percent": 37.5,
  "files_done": 1200, "files_total": 3200, "bytes_done": 104857600, "bytes_total": 279620266,
  "speed_bps": 52428800, "eta_s": 210, "current_file": "D:\\Data\\reports\\2026-10.pdf"
}
```

`phase`: `pre_events`, `vss`, `scan`, `copy`, `verify`, `retention`, `post_events`.

`POST /api/v1/agent/runs/finish`:

```json
{
  "run_id": "uuid", "task_id": "uuid", "status": "warning",
  "finished_at": "2026-10-12T21:04:40Z",
  "source_files": 3200, "source_bytes": 279620266,
  "files_processed": 3197, "bytes_written": 98112000,
  "errors": 0, "warnings": 3,
  "error_message": null,
  "destinations": [
    { "destination_id": "uuid", "status": "success", "set_name": "Documents 2026-10-12 21-00 (Incremental)", "bytes": 98112000, "error": null }
  ],
  "verify": { "performed": true, "ok": true, "scope": "new", "sets_checked": 1, "failed_sets": [] },
  "retention": { "deleted_sets": 1 },
  "databases": [
    { "engine": "mysql", "name": "shop", "bytes": 52428800, "ok": true, "error": null }
  ],
  "remote": null,
  "log_tail": "последние 100 строк журнала",
  "log_gz_b64": "есть только при status warning или error"
}
```

- `status`: `success`, `warning` (выполнено, но часть файлов пропущена), `error` или `aborted` (остановлено пользователем или командой).
- `source_files` и `source_bytes` описывают весь источник на момент запуска, даже при инкрементальной копии: по ним сервер ищет аномалии.
- `verify.scope`: `new` (проверена только что созданная копия) или `stored` (плановая проверка всех хранящихся наборов). Если какой-то набор не прошёл проверку, его имя попадает в `failed_sets`, а статус запуска становится `error` с `error_message` вида «Повреждён набор …».
- `databases` — дампы баз данных этого запуска (раздел 6.2 ТЗ клиента), по одному на базу; пользователи и права серверов сюда не входят. Поле необязательное: у задания без серверов баз его нет. Неудачный дамп делает запуск `error`; `error` дампа — причина словами.
- `remote` — только у задания с Linux-сервером (источник `ssh`, A.9), иначе `null` или нет поля:

  ```json
  "remote": { "helper_version": "1.0.0", "server_free_bytes": 52000000000, "files_changed": 120, "files_deleted": 3 }
  ```

  `helper_version` — версия custos-helper на сервере; `server_free_bytes` — свободное место на диске корней сервера (наименьшее), `null`, если сервер его не сообщил; `files_changed` — файлы, изменённые после прошлой копии; `files_deleted` — удалённые после неё, `null`, если прошлую копию прочитать не удалось. `source_files` и `source_bytes` у такого задания — файлы в корнях сервера плюс дампы, `databases` — базы сервера.
- `start` и `finish` идемпотентны по `run_id`. При недоступности сервера они сохраняются в локальной очереди агента и отправляются позже строго по порядку.

**Учётные данные** хранятся отдельно, задания ссылаются на них по `credential_id`. Одну учётку можно использовать в нескольких заданиях.

```json

```

Секрет хранится только на агенте под DPAPI и никогда не уходит на сервер.

Ключ `ssh_key` создаёт сам агент (в мастере Linux-сервера), задать его снаружи нельзя. У него есть открытая часть в строке формата OpenSSH, её можно показывать:

```json
{ "id": "uuid", "kind": "ssh_key", "user": "custos@vps.example.org", "has_secret": true, "public_key": "ssh-ed25519 AAAA… custos@PC01" }
```

Учётные данные облачных дисков (`gdrive`, `yadisk`, `dropbox`) создаёт только агент: аккаунт подключается через браузер на самом компьютере (6.3 ТЗ клиента). `user` — адрес почты или логин аккаунта, только для показа; секрет — токен обновления OAuth. В `secrets` команды `task.upsert` (A.4) такие виды не принимаются: агент отвечает `failed`. Задание с сайта ссылается на уже подключённый аккаунт по `credential_id`.

### A.10. Обновления агента

Команда `update.install` несёт `version`, `sha256` пакета и `signature`: подпись сервера (A.2) строки `"{version}\n{sha256}"`. Агент скачивает пакет `GET /api/v1/agent/updates/{version}` (запрос подписан как обычно, а двоичное тело ответа не подписывается, см. A.2), проверяет SHA-256 и подпись из команды, затем устанавливает. Пакет, не прошедший проверку, отклоняется. Новую версию сервер видит по следующему heartbeat. Пакет — zip с файлами программы и `manifest.json` (`version`, `min_protocol`, список файлов).

**Обновление 7-Zip.** Команда `sevenzip.update` несёт `version` (например `"24.09"`), `sha256` установщика и `signature`: подпись сервера строки `"7zip\n{version}\n{sha256}"`. Приставка `7zip` нужна, чтобы подпись установщика 7-Zip нельзя было выдать за подпись пакета CUSTOS той же версии и наоборот. Файл — официальный 64-битный установщик `7z{XXYY}-x64.exe` с github.com/ip7z/7zip, который сервер скачал один раз и сверил с SHA-256, опубликованной GitHub, или который администратор загрузил вручную. Агент скачивает его `GET /api/v1/agent/sevenzip/{version}`, проверяет SHA-256 и подпись из команды, достаёт `7z.dll` и заменяет им свой так же, как кнопкой обновления 7-Zip в программе: дожидается окончания заданий 7z, сохраняет прежний файл, проверяет новый и при неудаче возвращает прежний. Результат команды — `done`, `failed` (с причиной) или `rejected` (подпись не сошлась); новую версию сервер видит по `sevenzip_version` в следующем heartbeat. Агент, который не знает `sevenzip.update`, отклоняет её как неизвестную команду.

### A.11. Ошибки

Тело ошибки: `{"error": "код", "message": "текст"}`. Ответы с ошибками подписаны, как и все остальные (A.2). Агент выполняет действие из таблицы, только если подпись верна. Ответ без подписи или с неверной подписью, с любым кодом HTTP, агент обрабатывает по последней строке таблицы.

| HTTP | `error` | Действие агента |
|---|---|---|
| 400 | `bad_request` | Записать в журнал, не повторять |
| 401 | `bad_signature`, `clock_skew` | При `clock_skew` в теле есть `server_time`: записать «расходится время» |
| 403 | `pending`, `disabled`, `forbidden` | Ждать, отчёты держать в очереди. `forbidden`: адрес агента не входит в подсети, разрешённые для агентов в настройках сервера |
| 403 | `bad_registration_key` | Показать «ключ регистрации не подошёл», повторить регистрацию через 10 минут (A.3) |
| 404 | `unknown_agent` | Зарегистрироваться заново (A.3) |
| 413 | `too_large` | Отправить без `log_gz_b64` |
| 429 | `rate_limited` | Ждать `retry_after_s` секунд из тела ответа, но не больше часа |
| 5xx / нет связи / нет верной подписи | — | Повторять через 1, 2, 5, 10, 10… минут |

- **`429`.** Срок ожидания передаётся в теле: `{"error": "rate_limited", "message": "...", "retry_after_s": 120}`. Заголовок `Retry-After` с тем же значением сервер тоже ставит, но агент берёт значение из тела, потому что заголовки подписью не покрываются.
- **`413` для журнала по запросу.** Для `runs/{run_id}/log` (A.7) отправлять запрос без журнала бессмысленно: агент завершает команду `log.fetch` статусом `failed` с сообщением `too_large`.
- **Неподписанный `413`.** Его может вернуть сам nginx, не передав запрос в PHP, если `client_max_body_size` меньше 10 МБ. Если в запросе был `log_gz_b64`, агент поступает как при подписанном 413 и пишет в журнал совет проверить `client_max_body_size`. Иначе очередь отчётов застряла бы на одном большом запросе навсегда. Подделка такого ответа может только лишить сервер полного журнала, а его потом можно запросить командой `log.fetch`. Для остальных запросов неподписанный 413 — обычная недоступность сервера.
- Ответ на регистрацию проверяется по своим правилам (A.3).

| `error` | запуск | Ошибка | Копия не создана или создана не полностью |

### A.13. Журнал изменений

**Как меняется версия протокола.** Пока протокол нигде не развёрнут, правки вносятся без смены версии и только записываются сюда. После первого выпуска несовместимая правка (новое обязательное поле, другая строка подписи, другой смысл кода) увеличивает версию протокола в `X-Custos-Protocol`. Совместимая правка (новое необязательное поле, новый код статуса, который старая сторона может пропустить) записывается сюда без смены версии.

**28.10.2026 — протокол 1, до первого выпуска.** Уточнения по итогам разбора ТЗ. Версия не меняется, потому что протокол ещё нигде не работает.

- Приложение A вынесено из обоих ТЗ в этот файл и существует в одном экземпляре.
- A.2. `PATH` в подписи запроса считается относительно базового адреса API (`agent/heartbeat`), а не как полный путь на сервере. Подпапка и обратный прокси подписи не ломают.
- A.2. Подписан каждый ответ сервера, включая ошибки и ответы на регистрацию. В строку подписи ответа добавлен код HTTP: `"{STATUS}\n{TIME}\n{NONCE}\n{sha256hex(body)}"`. Ответ без верной подписи агент считает недоступностью сервера.
